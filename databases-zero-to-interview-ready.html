Chapter 1 — The Database Landscape

Before touching syntax, you need the mental map interviewers assume you already have. Every database in this book stores data, but they are optimized for different jobs.

1.1 What is a database, really?

A database is software that stores data durably (survives a crash/restart) and lets you query it efficiently, safely (even with many users at once), and reliably. The database engine (MySQL, PostgreSQL, SQLite) manages storage on disk, indexing, query planning, and concurrency. SQL is the language you use to talk to it.

1.2 The four tools in this book

ToolTypeRuns asBest known for
MySQLRelational (RDBMS)Client-server (daemon)Web apps, read-heavy workloads, huge ecosystem (WordPress, e-commerce)
PostgreSQLRelational (RDBMS), "object-relational"Client-server (daemon)Correctness, advanced SQL features, complex queries, JSON, extensibility
SQLiteRelational, embeddedIn-process library, single fileMobile apps, local storage, testing, small/medium single-writer apps
ChromaDBVector databaseEmbedded or client-serverStoring embeddings for semantic search / RAG in AI applications
Interviewers love the question: "When would you pick X over Y?" By the end of this book (Chapter 9) you'll have a crisp, memorized answer.

1.3 Relational vs. Vector — the core mental model

Relational databases store rows in tables and answer questions with exact logic: "find all orders where status = 'shipped' AND total > 100." Vector databases store numeric embeddings (arrays of floats representing meaning) and answer questions with similarity: "find the 5 documents whose meaning is closest to this query." Relational = exact match/filter. Vector = fuzzy/semantic match. Modern AI systems (RAG pipelines) often use both together — Postgres/MySQL for structured data, Chroma for semantic search over unstructured text.

1.4 SQL: one language, several dialects

MySQL, PostgreSQL, and SQLite all speak "SQL," and roughly 90% of the SQL you write is identical across all three (standard SQL). The differences show up in: data types, functions, auto-increment syntax, and advanced features. This book teaches you standard SQL first (Chapters 3–5, works almost everywhere), then dedicates a deep-dive chapter to each engine's specific quirks.

Practical checkpoint

No coding yet — just make sure you can answer out loud: "What's the difference between a relational database and a vector database, and why would a company use both?" You'll need this exact framing in interviews.

This chapter has no quiz — Chapter 1 is orientation. Testing starts in Chapter 2.

Chapter 2 — Setting Up Everything

You said you want this "from the beginning," so we install everything now. Pick your OS section. You only strictly need MySQL + one client to follow Chapters 3–5, but install all four so later chapters work immediately.

2.1 Installing MySQL

Windows

Download MySQL Installer from dev.mysql.com/downloads/installer/. Run it, choose "Server only" (or "Developer Default" if you also want Workbench, a GUI tool). During setup you'll set a root password — write it down, you'll use it constantly.

macOS

brew install mysql
brew services start mysql
mysql_secure_installation   # sets root password, removes test DB

Linux (Ubuntu/Debian)

sudo apt update
sudo apt install mysql-server
sudo systemctl start mysql
sudo mysql_secure_installation

Connect

mysql -u root -p

You should land on a mysql> prompt. Type SELECT VERSION(); then ; to confirm it works, then exit.

2.2 Installing PostgreSQL

Windows

Download the installer from postgresql.org/download/windows/ (EDB installer). It installs the server, pgAdmin (GUI), and command-line tools, and asks you to set a password for the postgres superuser.

macOS

brew install postgresql@16
brew services start postgresql@16

Linux (Ubuntu/Debian)

sudo apt install postgresql postgresql-contrib
sudo systemctl start postgresql

Connect

sudo -u postgres psql

Confirm with SELECT version(); then quit with \q.

2.3 Installing SQLite

SQLite needs almost no install — it's a single file library. Most systems already have it.

# macOS/Linux: check if it exists
sqlite3 --version

# Ubuntu, if missing:
sudo apt install sqlite3

# Windows: download the "sqlite-tools" zip from sqlite.org/download.html,
# unzip, and add the folder to your PATH.
# Create/open a database file (creates it if it doesn't exist)
sqlite3 mytest.db
sqlite> SELECT sqlite_version();
sqlite> .quit

2.4 Installing ChromaDB (Python)

ChromaDB is a Python-first vector database, usually run embedded inside your app. You need Python 3.9+.

python -m venv venv
source venv/bin/activate     # Windows: venv\Scripts\activate
pip install chromadb
# quick sanity check, in a Python shell
import chromadb
client = chromadb.Client()

DatabaseFree GUI options

Chapter 3 — SQL Fundamentals I: Tables, CRUD, Filtering

Everything here works, unmodified, in MySQL, PostgreSQL, and SQLite (minor notes flagged inline). We'll build a small company database and use it for the rest of the book.

3.1 Creating a database & table

CREATE DATABASE company;
USE company;                 -- MySQL / not needed in Postgres (use \c company) or SQLite (per-file)

CREATE TABLE employees (
    id          INT PRIMARY KEY AUTO_INCREMENT,   -- MySQL syntax
    first_name  VARCHAR(50) NOT NULL,
    last_name   VARCHAR(50) NOT NULL,
    email       VARCHAR(100) UNIQUE,
    department  VARCHAR(50),
    salary      DECIMAL(10,2),
    hire_date   DATE
);
AUTO_INCREMENT is MySQL-only. PostgreSQL uses id SERIAL PRIMARY KEY (or GENERATED ALWAYS AS IDENTITY in modern Postgres). SQLite uses id INTEGER PRIMARY KEY AUTOINCREMENT. Chapters 6–8 cover each engine's exact syntax.

3.2 Data types you must know

CategoryCommon types
IntegerINT, BIGINT, SMALLINT
Decimal/moneyDECIMAL(p,s) / NUMERIC(p,s) — exact, use for money
Floating pointFLOAT, DOUBLE — approximate, avoid for money
TextVARCHAR(n) (limited length), TEXT (unlimited)
Date/TimeDATE, TIME, DATETIME/TIMESTAMP
BooleanBOOLEAN (true native type in Postgres; MySQL stores as TINYINT(1))

3.3 Inserting data (Create)

INSERT INTO employees (first_name, last_name, email, department, salary, hire_date)
VALUES
('Alice', 'Khan', 'alice@corp.com', 'Engineering', 95000, '2021-03-15'),
('Bilal', 'Rahman', 'bilal@corp.com', 'Sales', 60000, '2020-07-01'),
('Chen', 'Wu', 'chen@corp.com', 'Engineering', 105000, '2019-11-20'),
('Dana', 'Osei', 'dana@corp.com', 'Marketing', 70000, '2022-01-10'),
('Evan', 'Lopez', 'evan@corp.com', 'Engineering', 88000, '2023-05-05');

3.4 Reading data (Read) — SELECT

SELECT * FROM employees;                       -- all columns, all rows
SELECT first_name, last_name FROM employees;    -- specific columns
SELECT * FROM employees WHERE department = 'Engineering';
SELECT * FROM employees WHERE salary > 80000 ORDER BY salary DESC;
SELECT * FROM employees LIMIT 3;                -- first 3 rows
SELECT DISTINCT department FROM employees;      -- unique values

3.5 Filtering — WHERE clause operators

=  !=  <>  >  <  >=  <=
WHERE salary BETWEEN 60000 AND 100000
WHERE department IN ('Sales', 'Marketing')
WHERE email LIKE '%corp.com'          -- % = any sequence, _ = single char
WHERE department IS NULL              -- never use "= NULL", it never matches
WHERE department IS NOT NULL
WHERE salary > 80000 AND department = 'Engineering'
WHERE salary > 80000 OR hire_date < '2021-01-01'

3.6 Updating data (Update)

UPDATE employees
SET salary = salary * 1.10
WHERE department = 'Engineering';
Always run the equivalent SELECT with the same WHERE clause first to see exactly which rows will be affected. An UPDATE or DELETE with no WHERE hits every row.

3.7 Deleting data (Delete)

DELETE FROM employees WHERE last_name = 'Lopez';
-- vs. TRUNCATE TABLE employees;  -- removes ALL rows fast, resets identity, can't be rolled back in MySQL (MyISAM)

3.8 Modifying table structure — ALTER

ALTER TABLE employees ADD COLUMN phone VARCHAR(20);
ALTER TABLE employees DROP COLUMN phone;
ALTER TABLE employees RENAME COLUMN department TO dept;   -- Postgres/MySQL 8+
ALTER TABLE employees MODIFY COLUMN salary DECIMAL(12,2); -- MySQL
-- Postgres equivalent: ALTER TABLE employees ALTER COLUMN salary TYPE DECIMAL(12,2);

3.9 Sorting, limiting, and aliases

SELECT first_name AS fname, salary AS pay
FROM employees
ORDER BY salary DESC, first_name ASC
LIMIT 5 OFFSET 2;   -- skip 2, take next 5 (pagination). SQLite/Postgres/MySQL all support this.

Chapter 4 — SQL Fundamentals II: Joins, Aggregation, Subqueries

This is the chapter interviewers actually test the most. Add a second table so we have something to join.

CREATE TABLE departments (
    id   INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) UNIQUE
);

CREATE TABLE projects (
    id            INT PRIMARY KEY AUTO_INCREMENT,
    title         VARCHAR(100),
    department_id INT,
    budget        DECIMAL(12,2),
    FOREIGN KEY (department_id) REFERENCES departments(id)
);

INSERT INTO departments (name) VALUES ('Engineering'), ('Sales'), ('Marketing'), ('HR');
INSERT INTO projects (title, department_id, budget) VALUES
('Platform Rewrite', 1, 250000),
('Q3 Outbound Campaign', 2, 40000),
('Brand Refresh', 3, 60000),
('Recruiting Drive', NULL, 15000);   -- unassigned department, on purpose

4.1 Aggregate functions

SELECT COUNT(*) FROM employees;
SELECT AVG(salary) FROM employees;
SELECT MIN(salary), MAX(salary) FROM employees;
SELECT SUM(budget) FROM projects;

4.2 GROUP BY and HAVING

SELECT department, COUNT(*) AS headcount, AVG(salary) AS avg_salary
FROM employees
GROUP BY department;

-- HAVING filters groups (after aggregation), WHERE filters rows (before aggregation)
SELECT department, COUNT(*) AS headcount
FROM employees
GROUP BY department
HAVING COUNT(*) > 1;
Interview one-liner: WHERE filters rows before grouping; HAVING filters groups after aggregation. You cannot use an aggregate function inside WHERE.

4.3 Joins — the interview centerpiece

Assume employees has a department_id column referencing departments.id (imagine we normalized it that way — see Chapter 5).

-- INNER JOIN: only rows that match in both tables
SELECT e.first_name, d.name AS department
FROM employees e
INNER JOIN departments d ON e.department_id = d.id;

-- LEFT JOIN: all rows from the left table, matched data from right (NULL if no match)
SELECT d.name, p.title
FROM departments d
LEFT JOIN projects p ON d.id = p.department_id;
-- HR department will appear with a NULL project, since it has none.

-- RIGHT JOIN: mirror of LEFT JOIN (not supported in SQLite; flip the tables instead)
SELECT p.title, d.name
FROM projects p
RIGHT JOIN departments d ON p.department_id = d.id;

-- FULL OUTER JOIN: everything from both sides (Postgres yes; MySQL: emulate with UNION of LEFT+RIGHT; SQLite 3.39+ supports it natively)
SELECT d.name, p.title
FROM departments d
FULL OUTER JOIN projects p ON d.id = p.department_id;

-- SELF JOIN: joining a table to itself (e.g., find employees in the same department)
SELECT a.first_name AS emp1, b.first_name AS emp2, a.department
FROM employees a
JOIN employees b ON a.department = b.department AND a.id < b.id;
Draw two circles (a Venn diagram) whenever asked about joins in an interview — INNER = intersection, LEFT = all of left circle, FULL OUTER = everything. It shows visual understanding, not memorized syntax.

4.4 Subqueries

-- Subquery in WHERE
SELECT first_name, salary FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- Subquery with IN
SELECT name FROM departments
WHERE id IN (SELECT department_id FROM projects WHERE budget > 50000);

-- Correlated subquery (references outer query — runs once per outer row)
SELECT e.first_name, e.salary, e.department
FROM employees e
WHERE e.salary = (SELECT MAX(salary) FROM employees e2 WHERE e2.department = e.department);

-- Subquery in FROM (derived table)
SELECT dept_avg.department, dept_avg.avg_sal
FROM (SELECT department, AVG(salary) AS avg_sal FROM employees GROUP BY department) AS dept_avg
WHERE dept_avg.avg_sal > 70000;

4.5 Set operations

SELECT name FROM departments
UNION
SELECT title FROM projects;      -- combines results, removes duplicates

SELECT name FROM departments
UNION ALL
SELECT title FROM projects;      -- keeps duplicates, faster

4.6 String, date & conditional functions you'll use constantly

SELECT CONCAT(first_name, ' ', last_name) AS full_name FROM employees;   -- Postgres/SQLite: also || operator
SELECT UPPER(first_name), LOWER(last_name) FROM employees;
SELECT YEAR(hire_date), MONTH(hire_date) FROM employees;   -- MySQL. Postgres: EXTRACT(YEAR FROM hire_date)
SELECT CASE
         WHEN salary > 90000 THEN 'Senior'
         WHEN salary > 70000 THEN 'Mid'
         ELSE 'Junior'
       END AS level
FROM employees;
SELECT COALESCE(department, 'Unassigned') FROM projects_by_department; -- fills NULLs with a default

Chapter 5 — Database Design: Keys, Relationships, Normalization

5.1 Keys

Key typeMeaning
Primary Key (PK)Uniquely identifies each row; cannot be NULL; one per table
Foreign Key (FK)Column referencing another table's PK; enforces referential integrity
Candidate KeyAny column (or set) that could serve as PK (e.g., email is unique too)
Composite KeyA PK made of two or more columns together
Unique KeyEnforces uniqueness but allows one NULL (unlike PK)

5.2 Relationship types

  • One-to-Many (most common): one department has many employees. FK lives on the "many" side (employees.department_id).
  • Many-to-Many: employees can work on many projects, and projects have many employees. Requires a junction table: employee_projects(employee_id, project_id).
  • One-to-One: e.g., employees and employee_passport_details — rare, usually merged into one table unless splitting for security/performance reasons.
CREATE TABLE employee_projects (
    employee_id INT,
    project_id  INT,
    role        VARCHAR(50),
    PRIMARY KEY (employee_id, project_id),
    FOREIGN KEY (employee_id) REFERENCES employees(id),
    FOREIGN KEY (project_id)  REFERENCES projects(id)
);

5.3 Normalization (interview favorite)

FormRule
1NFAtomic columns — no repeating groups/lists in one cell (e.g., no "PHP,MySQL,React" in one column)
2NF1NF + every non-key column depends on the whole primary key (matters for composite keys)
3NF2NF + no transitive dependencies (a non-key column shouldn't depend on another non-key column)
Classic 3NF violation: an orders table storing both customer_id and customer_email. Email depends on customer, not on the order — it belongs in the customers table. Fix: remove it from orders, join when needed.

5.4 Denormalization — when breaking the rules is correct

Normalization reduces redundancy but costs extra JOINs. High-read systems sometimes deliberately denormalize (duplicate data) to avoid expensive joins — e.g., storing product_name directly on an order_items row so historical orders don't change if the product is renamed later. Know this trade-off: normalize for correctness/write-safety, denormalize for read performance, and explain you'd only do the latter with a measured reason.

5.5 Constraints as design tools

CREATE TABLE orders (
    id         INT PRIMARY KEY AUTO_INCREMENT,
    customer_id INT NOT NULL,
    status     VARCHAR(20) DEFAULT 'pending' CHECK (status IN ('pending','shipped','cancelled')),
    total      DECIMAL(10,2) CHECK (total >= 0),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE CASCADE
);

ON DELETE CASCADE means deleting a customer auto-deletes their orders. Alternatives: ON DELETE SET NULL, ON DELETE RESTRICT (block the delete if children exist — often the safest default).

Practical exercise

  1. Design (on paper or in SQL) a many-to-many relationship between employees and projects.
  2. Take a badly-designed table with a comma-separated "skills" column and redesign it into 1NF.
  3. Add a CHECK constraint ensuring salary is always positive.

Chapter 6 — MySQL Deep Dive: Engines, Indexing, Transactions

6.1 Storage engines

MySQL's defining feature is pluggable storage engines — the same SQL front end, different storage back ends.

EngineTransactions?Row/table lockingUse case
InnoDB (default since 5.5)Yes (ACID)Row-levelDefault choice for almost everything today
MyISAMNoTable-levelLegacy; fast reads, no crash safety — avoid for new projects
MemoryNoTable-levelTemporary, in-RAM tables
CREATE TABLE t (id INT) ENGINE=InnoDB;
SHOW TABLE STATUS LIKE 'employees';   -- see which engine a table uses

6.2 MySQL-specific ID & type syntax

CREATE TABLE employees (
    id INT PRIMARY KEY AUTO_INCREMENT,
    ...
);
-- ENUM: MySQL-specific fixed value set
CREATE TABLE orders (
    status ENUM('pending','shipped','cancelled') DEFAULT 'pending'
);

6.3 Indexes

CREATE INDEX idx_lastname ON employees(last_name);
CREATE UNIQUE INDEX idx_email ON employees(email);
CREATE INDEX idx_dept_salary ON employees(department, salary);  -- composite index
SHOW INDEX FROM employees;
DROP INDEX idx_lastname ON employees;

InnoDB tables are stored as a clustered index on the primary key — rows are physically ordered by PK. Every secondary index stores the PK value, then a lookup ("bookmark lookup") back to the full row.

6.4 Transactions & isolation levels

START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- or ROLLBACK; on error

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- MySQL's InnoDB default
-- Other levels: READ UNCOMMITTED, READ COMMITTED, SERIALIZABLE

InnoDB's default is REPEATABLE READ (unusual — most databases default to READ COMMITTED). It uses MVCC (Multi-Version Concurrency Control) plus gap locks to prevent phantom reads within a transaction.

6.5 EXPLAIN and common performance moves

EXPLAIN SELECT * FROM employees WHERE department = 'Engineering';

Look at the type column: ALL (full table scan — bad on large tables), ref/range (using an index — good), const (best, single-row PK lookup). If type is ALL on a large filtered table, you're missing an index.

6.6 Users & privileges

CREATE USER 'app_user'@'localhost' IDENTIFIED BY 'strongpassword';
GRANT SELECT, INSERT, UPDATE ON company.* TO 'app_user'@'localhost';
FLUSH PRIVILEGES;
SHOW GRANTS FOR 'app_user'@'localhost';

6.7 Replication (know the concept for interviews)

MySQL replicates via the binary log: a primary server logs every write; replicas apply the same log to stay in sync. Classic use: one primary for writes, several replicas for reads, to scale read-heavy applications horizontally.

Practical exercise

  1. Confirm your employees table uses InnoDB via SHOW TABLE STATUS.
  2. Create a composite index on (department, salary) and run EXPLAIN on a query filtering by both.
  3. Wrap two UPDATE statements in a transaction, then intentionally ROLLBACK and verify nothing changed.
  4. Create a read-only MySQL user and confirm it can SELECT but not INSERT.

Chapter 7 — PostgreSQL Deep Dive

PostgreSQL is what interviewers mean by "advanced SQL." It's known for correctness, extensibility, and rich data types.

7.1 Identity columns & schemas

CREATE TABLE employees (
    id GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- modern replacement for SERIAL
    first_name VARCHAR(50) NOT NULL
);

CREATE SCHEMA hr;
CREATE TABLE hr.employees (...);   -- namespacing tables inside a database
SET search_path TO hr, public;

Postgres databases are organized into schemas (namespaces within one database) — MySQL doesn't have this; in MySQL, "database" and "schema" are the same thing.

7.2 JSON & JSONB — the killer feature

CREATE TABLE events (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload JSONB
);
INSERT INTO events (payload) VALUES ('{"type":"click","user_id":42,"tags":["homepage","cta"]}');

SELECT payload->>'type' AS event_type FROM events;             -- extract as text
SELECT payload->'tags' FROM events;                              -- extract as JSON
SELECT * FROM events WHERE payload @> '{"type":"click"}';        -- contains operator
CREATE INDEX idx_payload ON events USING GIN (payload);           -- fast JSON queries

JSONB stores JSON in a binary, indexable format (vs. plain JSON which just stores text) — always prefer JSONB.

7.3 Window functions

SELECT first_name, department, salary,
       RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank,
       AVG(salary) OVER (PARTITION BY department) AS dept_avg,
       salary - LAG(salary) OVER (PARTITION BY department ORDER BY hire_date) AS diff_from_prev_hire
FROM employees;

Unlike GROUP BY, window functions don't collapse rows — they attach a calculation to each row while still "seeing" a window/partition of related rows. Extremely common interview topic: RANK() vs DENSE_RANK() vs ROW_NUMBER() (RANK leaves gaps after ties, DENSE_RANK doesn't, ROW_NUMBER never ties).

7.4 Common Table Expressions (CTEs)

WITH dept_totals AS (
    SELECT department, SUM(salary) AS total_payroll
    FROM employees
    GROUP BY department
)
SELECT * FROM dept_totals WHERE total_payroll > 200000;

-- Recursive CTE: e.g., an org chart / manager hierarchy
WITH RECURSIVE org_chart AS (
    SELECT id, first_name, manager_id, 1 AS level
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.first_name, e.manager_id, oc.level + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart;

7.5 Array & other rich types

CREATE TABLE posts (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tags TEXT[]
);
INSERT INTO posts (tags) VALUES ('{"tech","sql","career"}');
SELECT * FROM posts WHERE 'sql' = ANY(tags);
-- Also notable: UUID, INET (IP addresses), full-text search TSVECTOR

7.6 Extensions

CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
SELECT uuid_generate_v4();

CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- fuzzy text search
CREATE EXTENSION IF NOT EXISTS vector;    -- pgvector! turns Postgres into a vector DB too (see Ch.12 note)

7.7 MVCC & VACUUM

Postgres, like InnoDB, uses MVCC — but instead of updating rows in place, an UPDATE writes a whole new row version and marks the old one dead. Dead rows accumulate ("bloat") until VACUUM reclaims the space. autovacuum normally handles this automatically; interviewers sometimes ask "what is VACUUM and why does Postgres need it" specifically because MySQL doesn't have an equivalent concept.

7.8 EXPLAIN ANALYZE

EXPLAIN ANALYZE SELECT * FROM employees WHERE department = 'Engineering';

Unlike plain EXPLAIN, ANALYZE actually runs the query and shows real timings alongside the planner's estimate — the standard tool for diagnosing slow Postgres queries.

Practical exercise

  2. Write a window function ranking employees by salary within department.
  3. Write a recursive CTE for a simple 2-level manager hierarchy.
  4. Run EXPLAIN ANALYZE on a filtered query and identify whether it used an index scan or a sequential scan.

Chapter 8 — SQLite Deep Dive

8.1 What makes SQLite different

SQLite is not a client-server database — it's a library linked directly into your application. The entire database (schema, data, indexes) lives in one ordinary file on disk. There's no server process, no network protocol, no username/password. This makes it the default choice for mobile apps (Android/iOS both ship it built-in), browsers, desktop apps, and local caches.

8.2 Dynamic typing ("type affinity")

CREATE TABLE notes (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT,
    body TEXT,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

Unlike MySQL/Postgres, SQLite mostly doesn't enforce column types strictly — a column declared TEXT can still store an integer. Types are a "hint" (affinity), not a hard constraint (this changed a bit with STRICT tables in newer SQLite, but assume flexible typing by default). Interviewers like this contrast question specifically.

8.3 Foreign keys are OFF by default

PRAGMA foreign_keys = ON;   -- must run this every connection, or FKs are not enforced!

8.4 Concurrency limits

Classic (rollback-journal) mode allows one writer at a time — other writers block/fail with "database is locked." WAL mode (Write-Ahead Logging) allows one writer concurrently with many readers, which is why almost every real SQLite deployment enables it:

PRAGMA journal_mode = WAL;

8.5 Practical use in code (Python example)

import sqlite3
conn = sqlite3.connect('practice.db')
cur = conn.cursor()
cur.execute("CREATE TABLE IF NOT EXISTS notes (id INTEGER PRIMARY KEY, title TEXT)")
cur.execute("INSERT INTO notes (title) VALUES (?)", ("First note",))
conn.commit()
for row in cur.execute("SELECT * FROM notes"):
    print(row)
conn.close()
Always use parameterized queries (? placeholders) instead of string-formatting SQL — this prevents SQL injection, and it matters in every database, not just SQLite.

8.6 When SQLite is the wrong choice

  • Multiple application servers writing to the same database over a network — SQLite has no network protocol.
  • High write concurrency from many simultaneous writers.
  • You need fine-grained user permissions/roles at the database level.

Practical exercise

  1. Create a SQLite database with a notes table and insert 3 rows via the command line.
  2. Turn on PRAGMA foreign_keys = ON and prove a bad foreign key insert now fails.
  3. Enable WAL mode and confirm with PRAGMA journal_mode;.
  4. Write a small Python script that inserts and reads rows using parameterized queries.

Chapter 10 — Indexing & Query Optimization

10.1 What an index actually is

An index is a separate, sorted data structure (almost always a B-Tree) that maps column values to row locations, so the engine can find rows without scanning the whole table. Without an index, any filter requires a full table scan — O(n). With an index, a lookup is roughly O(log n).

10.2 When indexes help — and when they hurt

  • Helps: columns used in WHERE, JOIN ON, ORDER BY, and GROUP BY, especially on large tables with selective filters.
  • Hurts: every index slows down INSERT/UPDATE/DELETE (the index must be updated too), and takes disk space. Don't index columns you never filter/sort/join on. Don't over-index small tables — a full scan of 200 rows is instant anyway.

10.3 Composite index column order matters

CREATE INDEX idx_dept_salary ON employees(department, salary);
-- This index helps:
--   WHERE department = 'Engineering'
--   WHERE department = 'Engineering' AND salary > 90000
-- This index does NOT help (efficiently):
--   WHERE salary > 90000   (department not specified — can't use the index's sort order first)

Rule of thumb: put the most selective / most frequently filtered-alone column first (a "leftmost prefix" rule applies across MySQL, Postgres, and SQLite).

10.4 Reading EXPLAIN output

EXPLAIN SELECT * FROM employees WHERE department = 'Engineering' AND salary > 90000;

Things to check: is it doing a full scan or an index scan/seek? How many rows does the planner estimate it will touch? Is it sorting in memory when it didn't need to (because an index could have supplied the order)?

10.5 N+1 query problem (very common interview/real-world bug)

-- BAD: one query per employee (N+1 queries total)
for emp in employees:
    db.query("SELECT * FROM projects WHERE employee_id = ?", emp.id)

-- GOOD: one query, using IN or a JOIN
SELECT * FROM projects WHERE employee_id IN (1,2,3,4,5);
-- or
SELECT e.*, p.* FROM employees e JOIN projects p ON p.employee_id = e.id;

10.6 Other optimization techniques

  • Covering indexes: an index that contains every column the query needs, so the engine never touches the actual table row.
  • LIMIT early: apply filters/limits before expensive joins where possible.
  • Avoid SELECT * in production code — fetch only needed columns (less I/O, enables covering indexes).
  • Avoid functions on indexed columns in WHERE — WHERE YEAR(hire_date) = 2024 can't use a plain index on hire_date; rewrite as a range: WHERE hire_date >= '2024-01-01' AND hire_date < '2025-01-01'.
  • Connection pooling: reuse DB connections instead of opening a new one per request.

Practical exercise

  1. Run EXPLAIN on a query with no index, note the scan type, then add an index and compare.
  2. Rewrite a "function-wrapped" WHERE clause into an index-friendly range condition.
  3. Identify an N+1 pattern in a small hypothetical loop and rewrite it as a single query.

Chapter 11 — Transactions, ACID & Concurrency

11.1 ACID — say this cold in interviews

LetterPropertyMeaning
AAtomicityA transaction's operations all succeed, or none do (all-or-nothing)
CConsistencyA transaction moves the database from one valid state to another, respecting constraints
IIsolationConcurrent transactions don't see each other's uncommitted changes
DDurabilityOnce committed, data survives a crash (written to durable storage)

11.2 Transaction basics

BEGIN;                       -- or START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                      -- makes it permanent
-- or ROLLBACK;               -- undoes everything since BEGIN

SAVEPOINT before_risky_step;
-- ... risky statement ...
ROLLBACK TO before_risky_step;   -- undo just that part, transaction still open

11.3 Isolation levels & the anomalies they prevent

LevelDirty readNon-repeatable readPhantom read
Read UncommittedPossiblePossiblePossible
Read CommittedPreventedPossiblePossible
Repeatable ReadPreventedPreventedPossible (MySQL InnoDB mostly prevents it too, via gap locks)
SerializablePreventedPreventedPrevented
  • Dirty read: reading another transaction's uncommitted change.
  • Non-repeatable read: re-reading the same row twice in one transaction gives different results because another transaction committed a change in between.
  • Phantom read: re-running the same filtered query gives a different set of rows because another transaction inserted/deleted matching rows.

PostgreSQL and MySQL both default differently: Postgres defaults to Read Committed; MySQL/InnoDB defaults to Repeatable Read. This is a frequently-asked distinction.

11.4 Locking

SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- row-level lock, blocks other writers until commit

Optimistic locking (check a version number before committing, retry on conflict) scales better under high contention than pessimistic locking (FOR UPDATE, hold a lock the whole time) — a common system-design follow-up question.

11.5 Deadlocks

Two transactions each hold a lock the other needs — the database detects this and kills one transaction (rolls it back) so the other can proceed. Application code should catch this and retry.

Practical exercise

  1. Open two terminal sessions to the same MySQL/Postgres database. In one, BEGIN a transaction and UPDATE a row without committing. In the other, try to SELECT ... FOR UPDATE the same row and observe the block.
  2. Commit the first transaction and watch the second unblock.
  3. Reproduce a non-repeatable read under Read Committed, then show Repeatable Read prevents it.

Chapter 12 — Vector Databases & ChromaDB (for AI/ML & RAG)

12.1 What's an embedding?

An embedding is a list of numbers (e.g., 384 or 1536 floats) produced by a machine learning model that represents the meaning of a piece of text (or image, audio, etc.). Texts with similar meaning end up with embeddings that are numerically close together in that high-dimensional space. This is what makes "semantic search" possible: instead of matching exact keywords, you match meaning.

12.2 Why not just use SQL for this?

Relational databases are built for exact filters and don't natively answer "which of these 1 million vectors is closest to this one?" efficiently. Vector databases build specialized indexes (commonly HNSW — Hierarchical Navigable Small World graphs) that make nearest-neighbor search over millions of high-dimensional vectors fast, using Approximate Nearest Neighbor (ANN) search — approximate because exact nearest-neighbor search at scale is too slow, and a very close match is good enough in practice.

12.3 Core Chroma concepts

ConceptMeaning
CollectionLike a "table" — a named group of embeddings + their metadata
DocumentThe original text (Chroma can auto-embed it for you)
EmbeddingThe vector representation of a document
MetadataStructured key/value data attached to each item (e.g., source, date, category) — filterable alongside vector search
QueryFind the top-k most similar items to a given query text/vector

12.4 Basic ChromaDB usage

import chromadb

# In-memory / local persistent client
client = chromadb.PersistentClient(path="./chroma_data")

collection = client.create_collection(name="articles")

collection.add(
    documents=[
        "MySQL is a popular relational database used in web applications.",
        "PostgreSQL supports advanced SQL features like window functions and JSONB.",
        "ChromaDB stores embeddings for fast semantic similarity search."
    ],
    metadatas=[
        {"topic": "mysql"},
        {"topic": "postgres"},
        {"topic": "vector-db"}
    ],
    ids=["doc1", "doc2", "doc3"]
)

results = collection.query(
    query_texts=["Which database is good for JSON data?"],
    n_results=2
)
print(results)   # returns the closest matching documents by meaning, not exact keywords

Notice you never wrote SQL, and you never manually created an embedding vector — Chroma uses a default embedding model under the hood (you can swap in OpenAI, Sentence-Transformers, or any custom embedding function).

12.5 Filtering with metadata (combining "SQL-like" filters with vector search)

results = collection.query(
    query_texts=["database performance tuning"],
    n_results=3,
    where={"topic": "mysql"}     # exact-match filter, applied alongside vector similarity
)

12.6 Updating & deleting

collection.update(ids=["doc1"], documents=["MySQL 8 added window functions and CTEs."])
collection.delete(ids=["doc3"])
collection.get(ids=["doc1"])          # fetch by id, no similarity search
print(collection.count())

12.7 Distance metrics

Similarity is measured with a distance function — most common is cosine similarity (angle between vectors — direction matters more than magnitude, standard for text embeddings), also common: Euclidean (L2) distance and dot product. Chroma lets you configure this per collection.

12.8 The RAG pattern (Retrieval-Augmented Generation)

This is the single most important real-world use case tying your AI/ML goals together:

  1. Split your documents into chunks, embed each chunk, store in Chroma.
  2. When a user asks a question, embed the question and query Chroma for the top-k most relevant chunks.
  3. Pass those chunks + the question into an LLM prompt ("answer using only this context").
  4. The LLM answers grounded in your actual data instead of hallucinating from training data alone.
# Simplified RAG skeleton
query = "How does MySQL replication work?"
relevant_chunks = collection.query(query_texts=[query], n_results=3)["documents"][0]
context = "\n".join(relevant_chunks)
prompt = f"Context:\n{context}\n\nQuestion: {query}\nAnswer using only the context above."
# send `prompt` to an LLM API

12.9 pgvector — the relational-database alternative

CREATE EXTENSION vector;
CREATE TABLE items (id bigserial PRIMARY KEY, content TEXT, embedding vector(384));
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops);
SELECT content FROM items ORDER BY embedding <=> '[0.12, 0.98, ...]' LIMIT 5;

The <=> operator is cosine distance in pgvector. Know this exists — "would you use Chroma or pgvector?" is a realistic interview question given your Postgres background (answer: pgvector if the vectors are secondary to a mostly-relational app already in Postgres; Chroma/a dedicated vector DB if vector search is the primary workload or you need to scale it independently).

Practical exercise

  1. Install chromadb, create a collection, add 5 short documents with metadata about a topic you know well.
  2. Query it with a question phrased completely differently from the document wording, and confirm semantic matching still finds the right document.
  3. Add a where metadata filter to a query.
  4. Build the minimal RAG skeleton above (retrieval only — you don't need a real LLM call to understand the pattern).

13.1 Rapid-fire conceptual questions (be able to answer in one breath)

  • What is a primary key vs foreign key? PK uniquely identifies a row in its own table; FK references a PK in another table to enforce a relationship.
  • What is normalization, and why would you denormalize? See Chapter 5.

  • What is an index, and its trade-off? Faster reads, slower writes, extra storage.

  • What's the N+1 problem? See Chapter 10.
  • SQL vs NoSQL? SQL = structured schema, strong consistency, relationships via joins. NoSQL (document/key-value/wide-column/graph) = flexible schema, often trades consistency for horizontal scalability. Vector databases are effectively a specialized NoSQL category for similarity search.

  • What's a stored procedure? Precompiled SQL logic saved in the database, callable by name — reduces round trips, but pushes business logic into the DB layer (a debated trade-off).

A6.2 — type = ALL means a full table scan — every row is examined. Fix by adding an appropriate index on the filtered/joined column(s).
A6.3 — REPEATABLE READ.

Chapter 7 Solutions

A7.1 — JSON stores the value as plain text (re-parsed on every access, no indexing support); JSONB stores it in a parsed binary format that supports indexing (e.g., GIN) and faster querying. Default to JSONB unless you specifically need to preserve exact text formatting/key order.

A7.4 — Postgres's MVCC creates a new row version on every UPDATE rather than overwriting in place, leaving "dead" old versions behind. VACUUM reclaims that space and updates statistics. A7.5 — EXPLAIN shows the planner's estimated query plan without running the query. EXPLAIN ANALYZE actually executes the query and reports real elapsed time and row counts alongside the plan, which is far more useful for diagnosing real slowness.

A10.5 — The database can't apply the index's precomputed sort order to a value it must first transform at query time — it would have to compute the function for every row, defeating the purpose of the index. Rewriting as a plain range comparison on the raw column lets the index be used directly.

Chapter 11 Solutions

A11.1 — Atomicity: all steps of a transaction happen, or none do. Consistency: a transaction only moves the database between valid states, respecting all constraints. Isolation: concurrent transactions don't interfere with each other's intermediate state. Durability: once committed, changes survive a crash.
A11.2 — A dirty read sees another transaction's uncommitted change (which might later be rolled back). A non-repeatable read sees a value change between two reads within the same transaction because another transaction committed a change in between.
A11.3 — MySQL (InnoDB) defaults to REPEATABLE READ; PostgreSQL defaults to READ COMMITTED.
A11.4 — Pessimistic locking grabs a lock upfront and holds it for the duration (e.g., SELECT ... FOR UPDATE), blocking other transactions — safe but can hurt throughput under contention. Optimistic locking assumes conflicts are rare: it reads data with a version number, and only checks at write time whether the version changed, retrying if a conflict occurred — better throughput under low contention.
A11.5 — A deadlock is when two (or more) transactions each hold a lock the other is waiting for, so neither can proceed. The database detects the cycle and automatically rolls back one of the transactions to break it; the application should catch that error and retry.

Chapter 12 Solutions

A12.1 — A numeric vector produced by a machine learning model that captures the meaning of a piece of content, such that semantically similar content produces numerically close vectors.
A12.2 — A B-Tree is built for exact-match/range lookups on ordered scalar values, not for measuring distance/similarity across many dimensions simultaneously — there's no natural "sort order" for high-dimensional vectors that a B-Tree could exploit.

Chapter 13 (Final) Solutions

AF.1 — SELECT MIN(salary) FROM (SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 3) t; — or, using a subquery approach: SELECT MAX(salary) FROM employees WHERE salary NOT IN (SELECT MAX(salary) FROM employees UNION SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees)); (the DISTINCT + LIMIT version above is the cleaner one to say out loud).
AF.2 — SELECT department, AVG(salary) FROM employees GROUP BY department HAVING COUNT(*) > 2;
AF.3 — MySQL and PostgreSQL are both full relational database servers for structured data — MySQL is simpler and extremely common in web apps, PostgreSQL has deeper advanced features. SQLite is a lightweight embedded database with no server, ideal for local/mobile apps. ChromaDB is a different category entirely — it stores AI embeddings and searches by meaning/similarity instead of exact values.
AF.4 — A clustered index physically orders the table's rows to match the index (a table can have only one, usually the primary key). A non-clustered/secondary index is a separate structure that stores index-column values plus a pointer (or, in InnoDB, the primary key) back to the actual row — a table can have many of these.
AF.5 — Structured relational tables (Postgres/MySQL) for tickets, users, statuses, timestamps, and relationships between them; a vector database (Chroma or pgvector) holding embedded chunks of support documentation/knowledge-base articles for semantic retrieval; the chatbot backend queries the relational DB for ticket context and the vector store for relevant documentation, then combines both into the LLM prompt (a RAG pattern layered on top of normal relational data).
