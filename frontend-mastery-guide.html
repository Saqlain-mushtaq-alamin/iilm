HTML & CSS Foundations

Semantic HTML, the box model, layout systems (Flexbox & Grid), spacing systems, and typography — the raw material every UI is built from.

1. Semantic HTML

Semantic tags describe meaning, not just appearance. Screen readers, SEO crawlers, and other developers all rely on this meaning. A <div> tells nothing; a <nav> tells everything.

Example
<header>
  <nav>
    <ul>
      <li><a href="/">Home</a></li>
    </ul>
  </nav>
</header>
<main>
  <article>
    <h1>Post title</h1>
    <p>Body copy...</p>
  </article>
</main>
<footer></footer>

2. The Box Model

Every element is a box made of content → padding → border → margin. The single most important CSS reset:

* { box-sizing: border-box; }

With border-box, width includes padding and border — so a width: 200px box stays 200px even after you add padding. Without it (the default content-box), padding adds on top of the width, which is almost never what you want.

3. Layout: Flexbox

Flexbox is for one-dimensional layout — a row or a column. Use it for nav bars, button groups, card headers, centering.

Example — a header with logo left, nav right
.header {
  display: flex;
  justify-content: space-between; /* main axis */
  align-items: center;          /* cross axis */
  gap: 24px;
}
.nav-links { display: flex; gap: 16px; }
PropertyControls

align-itemsalignment along the cross axis (row → vertical)

flex-wrap: wrapitems drop to a new line instead of overflowing

4. Layout: CSS Grid

Grid is for two-dimensional layout — rows AND columns together. Use it for page shells, image galleries, dashboards.

Example — a classic app shell
.app {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-rows: 64px 1fr;
  grid-template-areas:
    "sidebar header"
    "sidebar main";
  min-height: 100vh;
}
.sidebar { grid-area: sidebar; }
.header  { grid-area: header; }
.main    { grid-area: main; }
Rule of thumb: reach for Flexbox first. Reach for Grid the moment you catch yourself nesting flex containers to fake a 2D layout.

5. Spacing systems

Never use arbitrary pixel values (7px, 13px, 22px). Professional UIs use a spacing scale — a fixed set of values, usually multiples of 4 or 8 — applied consistently to padding, margin, and gap. This is what makes a UI "feel" designed instead of accidental.

:root {
  --space-1: 4px;   --space-2: 8px;   --space-3: 12px;
  --space-4: 16px;  --space-5: 24px;  --space-6: 32px;
  --space-7: 48px;  --space-8: 64px;
}
.card { padding: var(--space-5); gap: var(--space-3); }

Why it matters in an interview: being able to say "I use an 8px spacing scale, so paddings are 8/16/24/32" signals you think like a design-systems engineer, not someone eyeballing pixels.

6. Typography

  • Type scale — a fixed ramp of font sizes (e.g. 12/14/16/20/24/32/48px), usually following a ratio like 1.25 (major third). Don't invent a new size per component.
  • Line-height — body text: 1.5–1.6. Headings: 1.1–1.3 (tighter, because long lines of large text look loose otherwise).
  • Line length — keep body paragraphs to 45–75 characters per line (~max-width: 65ch) for readability.
  • Font weight — use weight, not just size, to build hierarchy: a 14px/600 label can outrank a 16px/400 paragraph.
:root {
  --text-xs: 0.75rem;  --text-sm: 0.875rem; --text-base: 1rem;
  --text-lg: 1.125rem; --text-xl: 1.25rem;  --text-2xl: 1.5rem;
  --text-3xl: 2rem;    --text-4xl: 2.5rem;
}
body { font-size: var(--text-base); line-height: 1.55; }
h1 { font-size: var(--text-4xl); line-height: 1.15; font-weight: 700; }
p  { max-width: 65ch; }

Interview Q&A

What's the difference between content-box and border-box?
With content-box (default), width/height apply only to the content area — padding and border add extra size. With border-box, width/height include padding and border, so the element's rendered size matches what you set. Almost every real project applies box-sizing: border-box globally.
Flexbox vs Grid — when do you use which?
Flexbox for one-dimensional layout (align items in a row or column, distribute space along one axis). Grid for two-dimensional layout (rows and columns together, e.g. a page shell or a gallery). They're complementary — Grid for the page skeleton, Flexbox inside individual components.
Explain z-index and stacking context.
z-index only works on positioned elements (not static) and only compares within the same stacking context. A new stacking context is created by things like position + z-index, opacity < 1, transform, or will-change. A high z-index inside a low-z-index stacking context still loses to a sibling context — this trips people up constantly.
Why prefer rem over px for font sizes?
rem is relative to the root font-size, so it respects the user's browser accessibility settings (increasing default text size). px is fixed and ignores user preference, hurting accessibility.
What is the CSS cascade, and how is specificity calculated?
When multiple rules target the same element, the browser resolves conflicts by: (1) importance (!important wins), (2) specificity — inline styles > IDs > classes/attributes/pseudo-classes > elements, (3) source order — later rules win ties. Specificity is often expressed as a tuple (inline, IDs, classes, elements).
What's the difference between visibility: hidden, display: none, and opacity: 0?
display: none removes the element from layout entirely (no space, not focusable, not read by screen readers). visibility: hidden keeps its layout space but hides it visually and from interaction. opacity: 0 keeps layout space AND stays interactive/focusable — it's only visually invisible.

Responsive & Adaptive UI Design

Building interfaces that work correctly from a 320px phone to a 4K monitor — mindset, techniques, and the traps that break layouts in interviews.

1. Mobile-first vs desktop-first

Mobile-first means you write the base CSS for the smallest screen, then add complexity with min-width media queries as the viewport grows. This is the industry default because it forces you to prioritize content, and because Tailwind, Bootstrap, and most modern systems are mobile-first by convention.

.card { display: block; } /* mobile default: stacked */

@media (min-width: 768px) {
  .card { display: grid; grid-template-columns: 1fr 1fr; } /* tablet+ */
}
@media (min-width: 1200px) {
  .card { grid-template-columns: repeat(3, 1fr); } /* desktop */
}

2. Fluid units over fixed pixels

3. clamp() for fluid typography

clamp(min, preferred, max) lets a value scale smoothly with the viewport but never go below or above a bound — no media query needed for type scaling.

h1 {
  font-size: clamp(1.75rem, 4vw + 1rem, 3.5rem);
}

4. Responsive images

<img
  src="photo-800.jpg"
  srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
  sizes="(max-width: 600px) 100vw, 50vw"
  alt="Product photo"
/>

The browser picks the smallest image that satisfies the rendered size at the current viewport — saving bandwidth on mobile automatically.

5. Container queries (the modern shift)

Media queries respond to the viewport. Container queries respond to the size of a parent container — critical for components (like a card) that get reused in a wide sidebar and a narrow one.

.card-wrapper { container-type: inline-size; }

@container (min-width: 400px) {
  .card { display: flex; flex-direction: row; }
}

7. Testing responsiveness properly

  • Resize the real browser window — don't just trust devtools device presets.
  • Test at odd widths (390px, 720px) not just exact breakpoints — real users land in between.
  • Check text reflow at 200% browser zoom (an accessibility requirement, WCAG 1.4.4).
  • Verify touch targets are ≥ 44×44px on mobile.
Common interview trap: "How would you build a responsive nav?" — the strong answer isn't just "hamburger menu on mobile." Talk through: what collapses first, how you handle touch targets, whether the menu should be a drawer or a dropdown, and how you'd keep it keyboard-accessible (focus trap, Escape to close).

Interview Q&A

What's the difference between responsive and adaptive design?
Responsive design uses fluid grids and CSS that continuously reflow to any viewport size. Adaptive design serves a small number of fixed layouts targeted at specific breakpoints (like distinct "mobile site" vs "desktop site"). Most modern web apps are responsive; adaptive is more common in native-feeling multi-layout apps.
What does the viewport meta tag do, and why is it required?
<meta name="viewport" content="width=device-width, initial-scale=1"> tells mobile browsers to render the page at the device's actual CSS pixel width instead of a default desktop-width canvas (usually 980px) that gets zoomed out. Without it, media queries never trigger correctly on phones.
How do container queries differ from media queries, and why were they needed?
Media queries only know the viewport size, so a reusable component can't adapt to the width of whatever container it's dropped into (a sidebar vs. a main column). Container queries let the component itself respond to its parent's size, making truly reusable, context-aware components possible.
How would you make an image both responsive AND avoid layout shift while it loads?
Set explicit width and height attributes (or an aspect-ratio in CSS) so the browser reserves the correct space before the image downloads, combined with max-width: 100%; height: auto; so it still scales fluidly. This prevents Cumulative Layout Shift (CLS).

JavaScript Fundamentals

Variables, types, functions, scope, this, arrays/objects, and the DOM — the bedrock everything else (React included) is built on.

1. var vs let vs const

2. Scope & closures

A closure is a function that "remembers" the variables from where it was defined, even after that outer function has finished running. This is the single most-tested JS concept in interviews.

Example — a counter factory
function createCounter() {
  let count = 0;
  return () => ++count;   // closes over `count`
}
const counter = createCounter();
counter(); // 1
counter(); // 2 — state persists between calls, privately
Classic gotcha — closures in loops: 
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
} // prints 3, 3, 3 — var is function-scoped, all closures share one `i`

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
} // prints 0, 1, 2 — let creates a new binding per iteration

3. this

this is determined by how a function is called, not where it's defined (except for arrow functions, which inherit this lexically from their enclosing scope).

const obj = {
  name: "card",
  regular() { return this.name; },      // this = obj when called as obj.regular()
  arrow: () => this.name,            // this = outer scope (NOT obj) — likely undefined
};
obj.regular(); // "card"
const fn = obj.regular;
fn();            // undefined — called with no receiver, `this` is undefined in strict mode

.call(), .apply(), and .bind() let you explicitly set this.

4. Arrays & objects — the methods you must know cold

const nums = [1, 2, 3, 4, 5];

nums.map(n => n * 2);            // [2,4,6,8,10] — transform each item
nums.filter(n => n % 2 === 0);   // [2,4] — keep matching items
nums.reduce((sum, n) => sum + n, 0); // 15 — fold into one value
nums.find(n => n > 3);           // 4 — first match
nums.some(n => n > 4);           // true — any match?
nums.every(n => n > 0);          // true — all match?

// spread / destructuring
const [first, ...rest] = nums;
const { name, ...others } = { name: "Ana", age: 30, city: "NYC" };
const merged = { ...defaults, ...overrides };

Immutability convention: in modern JS/React, prefer non-mutating operations — [...arr, item] not arr.push(item); arr.filter() not splice() — because React/state libraries detect changes by reference.

5. Equality: == vs ===

=== (strict equality) compares type and value with no coercion — always prefer it. == coerces types first, producing surprising results: '' == 0 is true, null == undefined is true.

6. Functions: declarations vs expressions vs arrow

function greet() {}           // declaration — hoisted entirely, usable before definition
const greet = function() {};  // expression — not hoisted with a value
const greet = () => {};      // arrow — no own `this`, no `arguments`, can't be a constructor

7. The DOM

const el = document.querySelector('.card');
el.addEventListener('click', (e) => {
  e.stopPropagation();     // stop bubbling to parent listeners
  console.log(e.target);   // the element actually clicked
});

// event delegation — one listener handles many children
document.querySelector('.list').addEventListener('click', (e) => {
  if (e.target.matches('.item')) { /* handle */ }
});

Event bubbling: events fire on the target, then bubble up through every ancestor. Delegation exploits this — attach one listener to a parent instead of one per child (better performance, works for dynamically-added children).

Interview Q&A

What is a closure? Give a practical use case.
A closure is a function bundled with references to its surrounding lexical scope, so it can access those variables even after the outer function returns. Practical uses: private state (module pattern), memoization caches, debounce/throttle functions, and React hooks themselves rely on closures.
Explain event bubbling vs event capturing.
An event travels in three phases: capture (from window down to the target), target, and bubble (back up to window). By default, addEventListener listens on the bubble phase; pass { capture: true } to listen during capture instead. Bubbling is what makes event delegation possible.
What's the difference between null and undefined?
undefined means a variable has been declared but not assigned a value (or a function returned nothing). null is an intentional, explicit "no value" assigned by the developer. typeof undefined === 'undefined'; typeof null === 'object' (a famous long-standing JS bug).
What does hoisting mean?
Before execution, the JS engine scans the scope and registers var declarations and function declarations. var is hoisted and initialized to undefined; function declarations are hoisted with their full body. let/const are hoisted but stay in the "temporal dead zone" — accessing them before the declaration line throws a ReferenceError.
How would you deep-clone an object in modern JS?
structuredClone(obj) is the modern built-in answer (handles nested objects, dates, maps — not functions). The older trick JSON.parse(JSON.stringify(obj)) works for plain data but silently drops functions, undefined, and loses Date/Map types.
Explain map() vs forEach().
map() returns a new array built from the callback's return values — use it when you need the transformed data. forEach() returns undefined and is purely for side effects (logging, mutating something external). Using forEach when you meant map is a common code-review flag.
What is prototypal inheritance?
Every JS object has an internal link ([[Prototype]], accessible via Object.getPrototypeOf) to another object. Property lookups walk up this prototype chain until found or the chain ends at null. class syntax is sugar over this same mechanism.

// 04 · javascript

JavaScript Advanced

The event loop, async patterns, modules, and design patterns — the concepts that separate "knows JS" from "reasons about JS."

1. The event loop (asked in almost every interview)

JS is single-threaded. The call stack runs synchronous code. Async work (timers, network, promises) is handed off to browser/Node APIs, and their callbacks queue up to run later:

  • Microtask queue — Promise .then, async/await, queueMicrotask. Runs first, and fully drains before the next step.
  • Macrotask queue — setTimeout, setInterval, I/O. Runs one task per event-loop tick.
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// Output: 1, 4, 3, 2
// sync code first → microtasks (promise) next → macrotasks (setTimeout) last

2. Promises & async/await

function fetchUser(id) {
  return new Promise((resolve, reject) => {
    if (id < 0) reject(new Error('invalid id'));
    else setTimeout(() => resolve({ id, name: 'Ana' }), 500);
  });
}

// async/await — same thing, reads like sync code
async function loadUser(id) {
  try {
    const user = await fetchUser(id);
    return user;
  } catch (err) {
    console.error('failed:', err.message);
  }
}

// run requests in PARALLEL, not sequentially
const [a, b] = await Promise.all([fetchUser(1), fetchUser(2)]);
Common mistake: awaiting inside a loop sequentially when requests are independent — for (const id of ids) await fetchUser(id) is slow. Use Promise.all(ids.map(fetchUser)) instead to run them concurrently.

5. Design patterns you'll actually use

Debounce & throttle

function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
} // waits for a pause — great for search-as-you-type

function throttle(fn, limit) {
  let waiting = false;
  return (...args) => {
    if (waiting) return;
    fn(...args);
    waiting = true;
    setTimeout(() => waiting = false, limit);
  };
} // runs at most once per interval — great for scroll/resize handlers

Module / factory / observer patterns

Modules (via ESM) give you privacy by closure. The observer pattern — objects subscribing to notifications — is the foundation of state management libraries (Redux, Zustand) and even React's own re-render mechanism.

6. try/catch, custom errors, and error boundaries at the JS level

class ApiError extends Error {
  constructor(message, status) {
    super(message);
    this.status = status;
    this.name = 'ApiError';
  }
}
try {
  throw new ApiError('Not found', 404);
} catch (e) {
  if (e instanceof ApiError) console.log(e.status);
}

Interview Q&A

Walk through the event loop with an example mixing setTimeout and Promises.
Synchronous code always runs first (the call stack). When it finishes, the engine drains the entire microtask queue (Promise callbacks) before touching the macrotask queue. Only after microtasks are empty does it run the next macrotask (a setTimeout callback). This is why Promise.resolve().then() always logs before a setTimeout(fn, 0).
What problem do Promises solve that plain callbacks didn't?
"Callback hell" — deeply nested, hard-to-read, hard-to-error-handle callbacks. Promises give you flat chaining (.then().then()), a single standard way to propagate errors (.catch), and combinators like Promise.all for coordinating multiple async operations.
Is async/await synchronous or asynchronous?
Still fully asynchronous — await just pauses execution of that function (not the whole program) until the promise settles, then resumes. It's syntactic sugar over .then() chains, not a different execution model.
Debounce vs throttle — give a real UI example of each.
Debounce delays execution until activity stops (e.g. a search input: wait until the user stops typing for 300ms before firing the API call). Throttle guarantees execution happens at most once per interval regardless of activity (e.g. a scroll handler updating a "read progress" bar at most every 100ms).
What is currying, and why would you use it?
Currying transforms a function of multiple arguments into a sequence of functions each taking one argument: const add = a => b => a + b. It enables partial application — pre-filling some arguments to create specialized reusable functions, common in functional composition and libraries like Redux's connect.

TypeScript

Static typing on top of JavaScript — catches bugs before runtime and is now the default expectation on most frontend teams.

1. Why TypeScript

TypeScript compiles to plain JS but adds a type-checking layer during development. It catches typos, wrong argument types, and null/undefined access before you ship — and it powers editor autocomplete, which is a huge productivity win on any team-sized codebase.

2. Basic types

let age: number = 30;
let name: string = "Ana";
let active: boolean = true;
let tags: string[] = ["a", "b"];
let pair: [string, number] = ["x", 1]; // tuple
let id: string | number = 5;              // union
let anything: unknown = fetchData();      // safer than `any` — must narrow before use

3. Interfaces & types

interface User {
  id: number;
  name: string;
  email?: string;        // optional property
  readonly createdAt: Date; // can't be reassigned after creation
}

type Status = 'idle' | 'loading' | 'success' | 'error'; // union of literals

function greet(user: User): string {
  return `Hello ${user.name}`;
}

interface vs type: interfaces can be re-opened and extended (declaration merging) and read more naturally for object shapes; type can express unions, tuples, and mapped types that interfaces can't. Convention: use interface for object/component-prop shapes, type for everything else.

4. Generics

Generics let a function or type work with any type while still preserving type-safety and relationships between inputs/outputs.

function firstItem<T>(arr: T[]): T | undefined {
  return arr[0];
}
firstItem([1, 2, 3]);      // inferred as number | undefined
firstItem(["a", "b"]);    // inferred as string | undefined

interface ApiResponse<T> {
  data: T;
  error: string | null;
}
const res: ApiResponse<User> = { data: user, error: null };

Interview Q&A

any vs unknown — what's the difference?
any disables type checking entirely — you can call anything on it with no error. unknown is type-safe: you must narrow it (via typeof, instanceof, or a type guard) before you're allowed to use it. Prefer unknown for values of uncertain shape (like API responses).
What is structural typing, and how does TS differ from nominal languages like Java?
TypeScript uses structural typing — two types are compatible if they have the same shape, regardless of name or declared inheritance. A Java-style nominal system instead requires explicit inheritance/implementation to consider two types related. This is why an object literal matching an interface's shape is assignable to it even without ever mentioning that interface.
Explain generics in one sentence, with an example of why they beat using any.
Generics let you write a function once that works with many types while preserving the type relationship between input and output — e.g. an array-of-T in, single-T out — whereas any would compile but lose all type-safety, letting mismatched types slip through undetected.
What does the satisfies operator do?
It checks that a value matches a type without widening or losing the value's more specific inferred type — useful when you want validation against a shape but still want autocomplete/literal-type precision on the resulting value, unlike a direct type annotation which would widen it.

1. Why React exists

React lets you describe UI as a function of state: UI = f(state). Instead of manually finding DOM nodes and mutating them, you describe what the UI should look like for a given state, and React figures out the minimal DOM changes needed (via the Virtual DOM diff).

Interview Q&A

What is the Virtual DOM and why does it help performance?
The Virtual DOM is a lightweight JS object tree representing the UI. On state change, React builds a new virtual tree, diffs it against the previous one ("reconciliation"), and applies only the minimal set of real DOM mutations needed — because real DOM writes are expensive, and batching/minimizing them is faster than naive re-rendering everything.
Why does React need a key prop on list items, and what goes wrong with using the array index?
Keys let React match old and new elements across renders to decide what to update, move, or discard. Using the index as a key breaks when items are reordered/inserted/removed — React matches by position, not identity, so component state (like an input's typed value) can end up attached to the wrong data row.
What's the difference between props and state?
Props are read-only data passed down from a parent — the component receiving them cannot change them. State is local, mutable (via its setter) data owned and managed by the component itself, and changing it triggers a re-render.
Why is direct state mutation (e.g. state.items.push(x)) wrong in React?
React detects changes by comparing references (Object.is), not deep equality. Mutating an object/array in place keeps the same reference, so React doesn't know anything changed and won't re-render. You must create a new array/object: setItems([...items, x]).
What happens if you forget the dependency array in useEffect?
The effect runs after every single render, which usually causes performance problems or infinite loops (especially if the effect itself sets state). Always pass a dependency array — [] for "run once," or the actual values the effect reads.
Controlled vs uncontrolled components — what's the difference?
A controlled component's value lives in React state and is set via value + onChange — React is the single source of truth. An uncontrolled component keeps its value in the DOM itself, read on demand via a ref (inputRef.current.value). Controlled is preferred for validation/formatting; uncontrolled is simpler for basic forms or file inputs.

React Advanced

Hooks in depth, Context, performance optimization, custom hooks, and the patterns senior React interviews probe for.

1. useRef

A ref is a mutable box that persists across renders without triggering a re-render when it changes — used for DOM access or storing a value you don't want to cause a re-render.

function TextInput() {
  const inputRef = useRef(null);
  useEffect(() => { inputRef.current.focus(); }, []);
  return <input ref={inputRef} />;
}

// storing a mutable value across renders (e.g. a previous value, an interval id)
const renderCount = useRef(0);
renderCount.current++; // doesn't cause a re-render, unlike setState

2. useContext — avoiding prop drilling

const ThemeContext = createContext('light');

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Toolbar />
    </ThemeContext.Provider>
  );
}
function Toolbar() {
  const theme = useContext(ThemeContext); // no prop drilling through intermediate components
  return <div className={theme}>...</div>;
}
Every consumer of a Context re-renders whenever the Provider's value changes — Context is not a performance optimization, it's a plumbing tool. For high-frequency state, use a dedicated state library instead.

3. useReducer — for complex state logic

function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'reset': return { count: 0 };
    default: throw new Error('unknown action');
  }
}
const [state, dispatch] = useReducer(reducer, { count: 0 });
dispatch({ type: 'increment' });

Reach for useReducer when the next state depends on complex logic across multiple sub-values, or when several event handlers need to update the same state in related ways.

4. Performance: memo, useMemo, useCallback

// memo — skip re-rendering a component if its props haven't changed
const Row = React.memo(function Row({ user }) {
  return <li>{user.name}</li>;
});

// useMemo — cache an expensive CALCULATION between renders
const sorted = useMemo(() => expensiveSort(items), [items]);

// useCallback — cache a FUNCTION reference so memo'd children don't re-render needlessly
const handleClick = useCallback(() => setCount(c => c + 1), []);
Interview-critical nuance: useCallback alone does nothing for performance — it only matters when the function is passed to a React.memo-wrapped child, because otherwise a new function reference every render would break that child's memoization. Don't wrap everything in useMemo/useCallback "just in case" — it has its own overhead and hurts readability.

5. Custom hooks

A custom hook is just a function starting with use that calls other hooks — the mechanism for extracting and reusing stateful logic across components.

function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}
// usage
const debouncedQuery = useDebounce(query, 300);

6. Rendering behavior & the rules of hooks

  • Only call hooks at the top level — never inside loops, conditions, or nested functions. React relies on call order to match hook state between renders.
  • Only call hooks from React function components or other custom hooks.
  • A component re-renders when its own state changes, its props change, or its parent re-renders (children re-render by default even with unchanged props, unless memoized).

7. Data fetching pattern & race conditions

useEffect(() => {
  let cancelled = false;
  fetchUser(id).then(data => {
    if (!cancelled) setUser(data); // avoid setting state after unmount / stale response
  });
  return () => { cancelled = true; };
}, [id]);

8. Error boundaries

class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  render() {
    return this.state.hasError ? <Fallback /> : this.props.children;
  }
}

Error boundaries must currently be class components — there's no hook equivalent — and they only catch errors during rendering, not in event handlers or async code (use try/catch there instead).

Interview Q&A

When would you use useReducer over useState?
When state transitions are complex, involve multiple related sub-values, or the next state depends heavily on the action taken rather than a simple new value — reducers centralize that transition logic in one place and make state changes more predictable and testable, similar to Redux.
Does useCallback improve performance by itself?
No — it only helps when the memoized function is passed to a child wrapped in React.memo (or used as a dependency elsewhere that needs referential stability, like a useEffect dependency). On its own it adds a small overhead and doesn't prevent the component's own re-render.
Why must hooks be called in the same order every render?
React doesn't use hook names — it tracks hooks per-component as an ordered list matched by call position. If a hook call is conditionally skipped, all subsequent hooks shift position and get matched to the wrong stored state, corrupting the component silently.
What's the danger of putting an object or array literal directly in a dependency array?
Object/array literals are a new reference on every render ({} !== {}), so an effect depending on one will re-run every render regardless of whether the actual values changed — often causing an infinite loop if the effect also sets state.
How do you prevent a stale closure bug in a useEffect?
Include every value the effect reads in the dependency array (as the exhaustive-deps ESLint rule enforces), or use the functional updater form of setState when you only need the latest state rather than reading it directly, so you don't need to list it as a dependency at all.
What is "lifting state up"?
Moving state from a child component to their closest common ancestor when two sibling components need to share and stay in sync with the same data — the ancestor then passes the state down as props and passes update functions down for the children to call.

The production React framework — routing, rendering strategies, data fetching, and the App Router mental model.

1. Why a framework on top of React

React alone is just a rendering library — it doesn't decide routing, data fetching, bundling, or how/where code runs. Next.js adds file-based routing, multiple rendering strategies (server vs client), built-in optimization (images, fonts, scripts), and API routes — turning React into a full application platform.

Interview Q&A

What's the difference between SSR, SSG, and ISR?
SSG generates HTML once at build time (fastest, but stale until the next build). SSR generates HTML fresh on every request (always current, but slower and more server load). ISR is a hybrid — pages are statically generated but automatically regenerated in the background after a set interval, giving near-static speed with periodic freshness.
What is a Server Component, and why does it matter for performance?
A Server Component renders entirely on the server and sends only HTML (no component JS) to the browser, reducing bundle size and enabling direct backend access without an API round-trip. It matters because most real apps have a lot of non-interactive UI (layout, static content) that never needed to ship JavaScript in the first place.
When do you need 'use client'?
Whenever a component needs interactivity or browser-only capabilities: hooks like useState/useEffect, event handlers, browser APIs (localStorage, window), or third-party libraries that assume a browser environment.
How does Next.js handle code-splitting?
Automatically, per route — each page's file-based route becomes its own JS bundle, so visiting /dashboard doesn't download the code for /settings. You can further split with dynamic() imports for heavy components used conditionally.
What problem do Server Actions solve?
They let you write a server-side mutation as a plain async function and call it directly from a component (even wire it straight to a form's action) without hand-building a separate REST/API route, reducing boilerplate for form submissions and data mutations.

function requireAuth(req, res, next) {

}

Interview Q&A

What is middleware in Express, and what does calling (or not calling) next() do?
Middleware is a function that runs during the request/response cycle before the final route handler, used for cross-cutting concerns like logging, auth, or parsing. Calling next() passes control to the next middleware/handler in the chain; failing to call it (without sending a response) leaves the request hanging forever.
Explain CORS in your own words.
Browsers enforce the Same-Origin Policy, blocking JS from one origin (domain+port+protocol) from reading responses from a different origin unless the server explicitly opts in via Access-Control-Allow-Origin and related headers. It's a browser-side security restriction, not a network-level block — the request often still reaches the server, but the browser withholds the response from your JS.
PUT vs PATCH — what's the difference?
PUT is meant to replace the entire resource with the payload provided (idempotent, full replacement). PATCH applies a partial update, changing only the fields included in the request body.
What does "idempotent" mean, and which HTTP methods are idempotent?
An idempotent operation produces the same result no matter how many times it's repeated. GET, PUT, and DELETE are idempotent (calling DELETE on an already-deleted resource still ends in "resource gone"). POST is not — submitting the same POST twice typically creates two resources.
Why does fetch() not throw on a 404 or 500 response?
fetch only rejects its promise for network-level failures (DNS failure, no connection). Any response that actually reaches the browser — even a 500 — resolves successfully; you must inspect response.ok or response.status yourself to detect an application-level error.

UI/UX Principles for Developers

The visual judgment that turns "technically correct" code into a UI that looks and feels professionally designed — how to translate a Figma file into pixel-accurate, consistent code.

1. Layout — hierarchy and grouping

  • Proximity — related items should be close together, unrelated items should have visible separation. If a label and its input have the same gap as two unrelated fields, the eye can't tell they're a group.
  • Alignment — every element should align to something (a grid column, another element's edge). Unaligned elements are the #1 subconscious signal of an "unpolished" UI.
  • Visual hierarchy — size, weight, color, and position tell the eye what to look at first. A page should have exactly one primary action that's visually dominant.
  • The 8pt grid — as in Chapter 1, base every layout dimension on multiples of a base unit (4 or 8px) so spacing always "lines up" between components.

2. Spacing — the detail that separates junior from senior work

The single highest-leverage skill: whitespace is not empty space to fill — it's what creates grouping and breathing room. When a design "feels cramped," the fix is almost always more spacing between unrelated groups, not smaller content.

Practical spacing checklist when implementing a design:

  • Vertical rhythm: consistent spacing between stacked elements (e.g. always 24px between form fields, 48px between page sections).
  • Padding should increase, not decrease, at larger breakpoints — mobile is cramped by necessity; desktop has room.
  • Nested spacing should be smaller than outer spacing (padding inside a card < gap between cards).

3. Typography as a system, not per-element choices

Example — a type scale used consistently
--text-xs: 12px;   /* captions, timestamps */
--text-sm: 14px;   /* secondary text, labels */
--text-base: 16px; /* body copy */
--text-lg: 18px;   /* lead paragraphs */
--text-xl: 24px;   /* h3 */
--text-2xl: 32px;  /* h2 */
--text-3xl: 48px;  /* h1 / hero */

Never eyeball a font-size. If a design calls for "slightly bigger," round to the nearest scale step — this is what "systemized" means, and it's what makes a UI feel coherent across 50 screens instead of hand-crafted per page.

4. Consistency — the trait that most separates good UIs from bad ones

  • Component reuse — the same button should look and behave identically everywhere it appears. If "Save" is blue and filled on one screen and outlined on another, that's a bug, not a style choice.
  • Naming consistency — the same action should always be labeled the same word (don't call it "Delete" here and "Remove" there).
  • Interaction consistency — if clicking a card opens a detail view in one place, it should everywhere; don't make some cards clickable and visually identical cards not.
  • A design system / token file is how teams enforce this at scale — colors, spacing, radii, shadows, and type all reference one source of truth instead of being redefined per component.

5. Translating a design file (Figma) into pixel-accurate code

  1. Inspect, don't guess. Use Figma's "Inspect" panel to get exact spacing, font sizes, colors (hex/rgba), and border-radius — never eyeball values from the screenshot.
  2. Extract tokens first. Before writing a single component, pull out the color palette, type scale, and spacing scale used across the whole file — most designs reuse a small set of values even if that's not obvious at a glance.
  3. Match structure, not just appearance. If the design shows a card with icon + title + description, structure your markup that way (semantically), then style — don't build one giant absolutely-positioned div that happens to look right at one screen size.
  4. Verify at multiple states the static design doesn't show: empty state, loading state, error state, long text overflow, hover/focus. A real interview task often specifically checks whether you thought about these.
  5. Compare side-by-side. Overlay your build against the design (or flip between browser tabs) at the same zoom level and check alignment, spacing, and type size pixel-by-pixel.

6. Color & contrast

  • Body text needs a contrast ratio of at least 4.5:1 against its background (WCAG AA) — large text (18px+/bold) needs at least 3:1.
  • Never convey information (errors, required fields) through color alone — pair it with an icon or text for colorblind users.
  • Build a limited palette: 1 primary, 1–2 accent, a gray scale (5–7 steps), and semantic colors (success/warning/error/info). Resist adding a new color per feature.

7. Accessibility as part of "pixel-accurate"

  • Every interactive element needs a visible focus state — don't remove outline without replacing it.
  • Touch/click targets should be at least 44×44px, even if the visual icon is smaller (pad the hit area).
  • Use real semantic elements (<button>, not a styled <div onClick>) so keyboard and screen-reader users get built-in behavior for free.

Interview Q&A

How do you approach turning a Figma design into a component?
Inspect exact values rather than eyeballing (spacing, colors, type), identify which values map to existing design tokens vs. new ones, structure the markup semantically to match the content hierarchy (not just visual position), build states the static file doesn't show (empty/loading/error/hover), and verify side-by-side at the actual target viewport widths.
What makes a UI feel "consistent" technically?
A shared, limited set of design tokens (color, spacing, type, radius, shadow) referenced everywhere instead of one-off values, componentized UI elements reused rather than rebuilt per screen, and consistent naming/behavior for the same actions across the whole app.
What's the difference between UI and UX?
UI (User Interface) is the visual and interactive surface — layout, color, typography, components. UX (User Experience) is the broader outcome — whether the product is usable, efficient, and satisfying to accomplish a goal with, including flows, information architecture, and error recovery, independent of visual styling.
How would you ensure your implementation is accessible, not just visually correct?
Use semantic HTML elements instead of generic divs with click handlers, ensure sufficient color contrast, preserve visible focus indicators, make sure all functionality is reachable by keyboard alone, add proper labels/alt text, and test touch target sizes on mobile.

Debugging Frontend Issues

A systematic process for finding bugs — plus the specific DevTools workflows for CSS layout, JS logic, and network issues.

1. A repeatable debugging process

  1. Reproduce reliably. Find the exact steps that trigger the bug every time — an intermittent bug you can't reproduce can't be fixed with confidence.
  2. Isolate. Remove variables until you find the minimal case that still fails (comment out code, test in an empty component, bisect).
  3. Form a hypothesis. Based on the symptom, guess the likely cause before changing code — undirected trial-and-error wastes time.
  4. Verify with evidence (a log, a breakpoint, a network tab) rather than assuming the fix worked.
  5. Fix the root cause, not just the symptom — and add a test or comment explaining why, so it doesn't regress.

2. Console methods beyond console.log

console.table(users);          // renders an array of objects as a readable table
console.group('Fetch user');
console.log('starting...');
console.groupEnd();
console.trace();               // prints the current call stack
console.assert(count > 0, 'count should be positive'); // logs only if condition is false
console.time('sort'); sortItems(); console.timeEnd('sort'); // measure duration

3. Debugging JS logic with breakpoints (not just console.log)

function calculateTotal(items) {
  debugger; // pauses execution here when devtools is open — inspect variables live
  return items.reduce((sum, i) => sum + i.price, 0);
}

Breakpoints let you inspect the exact call stack and variable values at the moment of failure — far more reliable than sprinkling console.log and re-running. Conditional breakpoints (right-click a line number in DevTools) let you pause only on the Nth iteration or a specific condition.

4. Debugging CSS layout issues

  • The Elements panel's "Computed" tab shows the final resolved value of any property after the cascade — use it to find which rule actually won.
  • Toggle outline: 1px solid red on * temporarily to visualize every box's boundaries when a layout looks broken.
  • The Layout panel in Chrome DevTools visually overlays Flexbox/Grid lines and gaps directly on the page.
  • Common cause checklist for "why isn't this centering/aligning": is the parent actually a flex/grid container? Is there a default margin/padding from the browser's user-agent stylesheet? Is a fixed height clipping content? Is box-sizing set consistently?

5. Debugging with the Network tab

  • Check the actual response status and body — a 200 with an error message in the body (a common backend mistake) looks fine at a glance but isn't.
  • Check request headers/payload to confirm the frontend is sending what you think it's sending (auth token present? correct Content-Type?).
  • Use the "waterfall" view to spot slow or blocking requests, or requests firing more often than expected (a classic sign of a missing useEffect dependency array or a re-render loop).

6. React-specific debugging

  • React DevTools — inspect the component tree, current props/state, and use the "highlight updates" setting to visually see which components re-render and how often.
  • An infinite re-render loop is almost always: setting state directly in the render body (not in an effect/handler), or a useEffect with a dependency that's a new object/array/function reference every render.
  • "Why did this re-render?" — check: did props change (by reference)? Did state change? Did the parent re-render (and this child isn't memoized)? Did context change?
Example — a real infinite-loop bug and the fix
// ❌ bug: new object literal every render → effect re-runs forever
const options = { limit: 10 };
useEffect(() => { fetchData(options).then(setData); }, [options]);

// ✅ fix: move the stable value outside the component, or memoize it
const options = useMemo(() => ({ limit: 10 }), []);
useEffect(() => { fetchData(options).then(setData); }, [options]);

7. Reading a stack trace

Read from the top: the first line is the error and where it was thrown; each subsequent line is a calling frame, in order, down to where execution originally started. Look for the first frame that's your code (not a library) — that's usually where the real bug lives, even if the crash surfaced deeper inside a dependency.

Interview Q&A

Walk me through how you'd debug a page that's blank with no visible errors.
Check the console for silent errors first (sometimes filtered by log level). Check the Network tab for a failed critical request (JS bundle 404, API call failing and blocking render). Check React DevTools to see if the component tree even mounted. Check for a thrown error being swallowed by a missing error boundary. Bisect by commenting out recently changed code.
A component re-renders way more than expected. How do you find out why?
Use React DevTools' Profiler/"highlight updates" to see which components re-render and how often. Check whether a parent re-renders and this child isn't memoized, whether a Context value is a new object each render, or whether a useEffect dependency is a non-stable reference (object/array/function) causing an update-triggering loop.
How do you debug a CSS layout that "looks broken" with no console errors (since CSS doesn't throw)?
Inspect the element's Computed styles to see what actually won the cascade, temporarily outline all elements to visualize box boundaries, check for default browser margins/padding, and use the Layout panel to visualize flex/grid lines directly on the page.
What's the value of a conditional breakpoint over a console.log inside a loop?
A console.log inside a loop that runs 1000 times floods the console and you have to scroll to find the relevant iteration. A conditional breakpoint pauses execution only when your condition is true, letting you inspect the exact state at the moment that matters without noise.

Performance Optimization

How browsers render, what actually makes a page feel slow, and the concrete techniques to fix it — for both load time and runtime interactivity.

1. The critical rendering path

Browser flow: parse HTML → build DOM → fetch/parse CSS → build CSSOM → combine into a Render Tree → Layout (compute geometry) → Paint (fill pixels) → Composite (layer onto the screen). Anything that forces this to repeat — resizing an element in a loop, reading layout properties right after writing them — is expensive.

2. Core Web Vitals — the metrics that actually get measured

MetricMeasuresGood threshold
LCP (Largest Contentful Paint)time until the biggest visible element renders< 2.5s
INP (Interaction to Next Paint)responsiveness of the page to user input< 200ms
CLS (Cumulative Layout Shift)visual stability — how much content jumps around while loading< 0.1

3. Reducing bundle size & load time

// code-splitting: load a heavy component only when needed
const Chart = React.lazy(() => import('./Chart'));

<Suspense fallback={<Spinner />}>
  <Chart />
</Suspense>
  • Code-split by route — don't ship the admin dashboard's JS to a visitor on the landing page.
  • Tree-shake — import only what you use (import { debounce } from 'lodash-es', not the whole library).
  • Lazy-load below-the-fold images with loading="lazy".
  • Compress & serve modern image formats (WebP/AVIF) and correctly sized srcsets (see Chapter 2).

4. Avoiding layout thrashing

Example — forced synchronous layout (bad) vs batched (good)
// ❌ reading then writing layout in a loop forces a re-layout every iteration
boxes.forEach(box => {
  const h = box.offsetHeight; // READ — triggers layout
  box.style.height = h + 10 + 'px'; // WRITE — invalidates layout
});

// ✅ batch all reads first, then all writes
const heights = boxes.map(box => box.offsetHeight); // all reads
boxes.forEach((box, i) => box.style.height = heights[i] + 10 + 'px'); // all writes

5. Animating cheaply

Only transform and opacity can be animated on the compositor thread, skipping layout and paint entirely — everything else (animating width, top, margin) forces layout recalculation on every frame.

/* ❌ expensive — triggers layout every frame */
.box { transition: left 0.3s; }
.box.open { left: 300px; }

/* ✅ cheap — GPU-composited, no layout recalculation */
.box { transition: transform 0.3s; }
.box.open { transform: translateX(300px); }

6. React-specific performance

  • Virtualize long lists (render only visible rows) with a library like react-window when rendering hundreds/thousands of items.
  • Memoize expensive derived calculations (useMemo) and avoid unnecessary re-renders of large subtrees (React.memo), but only after profiling shows it's needed — premature memoization adds complexity for no measured benefit.
  • Avoid creating new functions/objects as props to memoized children on every render (breaks the memoization).
  • Debounce expensive operations triggered by fast-firing events (typing, scrolling, resizing).

7. Measuring, not guessing

  • Lighthouse (Chrome DevTools) — automated audit of performance, accessibility, and best practices with a numeric score and specific fixes.
  • Performance panel — records a timeline of scripting, rendering, and painting to find exactly which function is slow.
  • React Profiler — measures render duration per component per commit.
Golden rule: never optimize based on a hunch. Profile first, find the actual bottleneck, fix that specific thing, then measure again to confirm it helped.

Interview Q&A

What are the Core Web Vitals and why do they matter?
LCP (loading speed of the main content), INP (input responsiveness), and CLS (visual stability) are Google's standardized UX metrics — they matter both for real user experience and because they factor into search ranking, giving teams concrete, measurable performance targets instead of vague "feels slow" complaints.
Why is animating transform cheaper than animating width or top?
transform and opacity can be handled entirely by the compositor/GPU without recalculating layout or repainting the rest of the page. Properties like width, top, or margin change an element's geometry, forcing the browser to redo layout and paint on every animation frame — much more expensive.
What is layout thrashing and how do you avoid it?
It happens when you interleave DOM reads (like offsetHeight) and writes (like style.height =) in a loop — each read forces the browser to flush pending layout changes synchronously, so alternating read/write causes layout to run repeatedly instead of once. The fix is batching: do all reads first, store the values, then do all writes.
How would you optimize a list rendering 10,000 items?
Virtualize it — only render the rows currently visible in the viewport (plus a small buffer), recycling DOM nodes as the user scrolls, using a library like react-window or TanStack Virtual, rather than mounting 10,000 real DOM nodes at once.
What's the danger of over-using useMemo/React.memo everywhere?
Memoization itself has a cost (storing and comparing previous values/props) and adds code complexity. Applied indiscriminately without profiling, it can add overhead without meaningfully reducing re-renders, and it obscures simpler code for a "just in case" optimization that was never actually the bottleneck.

Interview Question Bank & Mock Problems

Cumulative practice — rapid-fire conceptual questions, live-coding style problems, and a frontend "system design" style question, mixing every topic in this guide.

1. Rapid-fire round (aim to answer each in under 60 seconds)

What happens when you type a URL into the browser and press Enter?
DNS lookup resolves the domain to an IP → browser opens a TCP connection (TLS handshake if HTTPS) → sends an HTTP request → server responds with HTML → browser parses HTML into the DOM while fetching CSS/JS → CSSOM built → DOM+CSSOM combine into the render tree → layout → paint → composite → page becomes interactive as JS finishes executing.
What's the difference between a library and a framework?
A library (like React for rendering) is something you call into on your own terms and control flow. A framework (like Next.js or Angular) dictates the overall structure and calls your code — "inversion of control." React itself is technically a library; the ecosystem around it (Next.js) becomes a framework.
Explain the difference between authentication and authorization.
Authentication verifies who you are (login, password, tokens). Authorization determines what you're allowed to do once identified (permissions, roles). A logged-in user is authenticated; whether they can delete another user's post is an authorization decision.
What is a memory leak in a frontend context, and give a common React cause.
Memory that's no longer needed but isn't released because something still references it. Common React cause: an async operation (timer, subscription, fetch) that sets state after the component has unmounted, or an event listener added in useEffect without a cleanup function removing it.
What is a Progressive Web App (PWA)?
A web app enhanced with capabilities traditionally reserved for native apps — offline support via a Service Worker, install-to-homescreen via a manifest file, and push notifications — while still being a normal website under the hood.
What's the difference between localStorage, sessionStorage, and cookies?
localStorage persists indefinitely with no expiry, scoped per-origin, ~5-10MB, not sent to the server automatically. sessionStorage is the same API but cleared when the tab closes. Cookies are small (~4KB), can have an expiry, and are automatically sent with every matching HTTP request — which is why they're used for session/auth tokens but need care around size and security (HttpOnly, Secure, SameSite flags).
What is XSS, and how does React help prevent it by default?
Cross-Site Scripting — an attacker injects malicious script that executes in another user's browser, often via unescaped user input rendered as HTML. React escapes all values rendered via JSX {} by default, converting them to text rather than executing them as markup — the risk reappears specifically when using dangerouslySetInnerHTML, which should only ever receive sanitized content.
What is a race condition in a frontend app? Give an example.
A bug caused by the order of async operations completing unpredictably. Example: a user types "a" then quickly "ab" in a search box, firing two API requests; if the "a" request happens to resolve after the "ab" request, the UI ends up showing stale results for "a" even though "ab" is the latest input. Fixed by tracking request order/cancellation (see Chapter 7).
