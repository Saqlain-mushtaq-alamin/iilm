1.1What is an API?

API means Application Programming Interface. It is a set of rules that lets one program talk to another program.

Think about a restaurant. You (the client) do not walk into the kitchen. You tell the waiter what you want, the waiter tells the kitchen (the server), and the waiter brings back your food. The waiter is the API: a clear, fixed way to ask for things.

A web API works over the internet using HTTP. A mobile app that shows the weather does not know the weather itself. It asks a weather API: "give me today's weather for Dhaka", and the API answers with data (usually JSON).

1.2Client, server and the request–response cycle

Two rules to remember: (1) the client always starts the conversation, and (2) every request gets exactly one response. HTTP is stateless: the server does not remember your last request unless you send something (a token, a cookie) that reminds it.

1.4Anatomy of a request and a response

A raw HTTP message has three parts: a start line, headers, and an optional body.

The request start line has method + path + version. The response start line has version + status code + reason. The empty line between headers and body is required.

1.9HTTPS, cookies and tokens (short version)

  • HTTPS = HTTP inside TLS. It encrypts data, proves the server's identity, and stops tampering. Always use it in production.
  • Cookies are small pieces of data the browser stores and sends automatically. Good for browser apps and sessions.
  • Tokens (like JWT) are sent by your code in the Authorization header. Good for mobile apps and APIs. (Chapter 11)
  • HTTP versions: 1.1 (text, one request per connection at a time), 2 (binary, many requests over one connection), 3 (runs on QUIC/UDP, faster on bad networks). Your API code stays the same.

1.10Try it: talk to a real API with curl

Open a terminal. -i shows headers, -X sets the method, -H adds a header, -d sends a body.

Interview: "What happens when you type a URL and press Enter?"

Browser parses the URL → DNS lookup finds the IP → TCP connection → TLS handshake (for https) → browser sends an HTTP GET request → server processes it and returns a response → browser renders HTML and loads more resources (CSS, JS, images), each with its own request. Give this in 6–7 clear steps and you are ahead of most candidates.

2.1What is REST?

REST = Representational State Transfer. Roy Fielding described it in his PhD thesis (2000). Important: REST is not a protocol or a standard. It is an architectural style, a set of rules. An API that follows the rules is called RESTful.

The core idea: everything is a resource (a user, an order, a book). Each resource has a URL. You use standard HTTP methods to work with it. The server sends back a representation of the resource (usually JSON).

2.2The REST constraints

ConstraintSimple meaningWhy it helps
Client–serverUI and data storage are separateEach side can change and scale alone
StatelessEvery request has all the info the server needs. No session stored on the serverAny server can handle any request, so you can add more servers easily
CacheableResponses say if they can be cachedLess load, faster responses
Uniform interfaceSame simple rules everywhere: resource URLs, standard methods, self-descriptive messages, links (HATEOAS)Easy to learn and use
Layered systemClient cannot tell if it talks to the real server or a proxy / load balancer / cacheAdd security, caching, balancing without changing clients
Code on demand (optional)Server can send code (e.g. JavaScript) to run on the clientRarely used in APIs
Statelessness in practice

Bad: login once, the server remembers "this connection is Ana", later requests carry no identity. Good: every request carries a token (Authorization: Bearer ...), so the server can verify it every time without remembering anything.

2.3Resources and URL design

Rules that make URLs clean:

  • Use nouns, not verbs. The HTTP method is already the verb.
  • Use plural names for collections: /users, /orders.
  • Show relations with hierarchy: /users/7/orders. Do not nest deeper than 2 levels.
  • Use lowercase and hyphens: /order-items. No trailing slash, no file extensions.
  • Filtering, sorting and paging go in the query string, not the path.
BadGood
GET /getAllUsersGET /users
POST /createUserPOST /users
GET /user/delete?id=5DELETE /users/5
GET /getOrdersOfUser/7GET /users/7/orders
GET /users/activeGET /users?status=active

What about actions that are not CRUD, like "publish an article" or "cancel an order"? Model them as a sub-resource or a state change: POST /orders/9/cancel or PATCH /orders/9 {"status": "cancelled"}. Be consistent.

2.5Safe and idempotent — the interview favourite

  • GET /books/5 ×10 → nothing changes. Safe + idempotent.
  • PUT /books/5 with the same body ×10 → book 5 ends in the same state. Idempotent.
  • DELETE /books/5 ×10 → first call 204, next calls 404, but the server state is the same (book is gone). Idempotent (the response code may differ).
  • POST /books ×10 → ten new books. Not idempotent.

Why it matters: networks fail. If a client does not get a response, it may retry. Retrying an idempotent call is safe. To make a POST safe to retry (payments!), let the client send an Idempotency-Key header; the server remembers the key and returns the first result for repeated keys.

PUT vs PATCH: PUT sends the whole resource and replaces it (missing fields are reset or rejected). PATCH sends only the changes.

2.6Choosing status codes

  • Created something → 201 + Location header. Deleted, nothing to return → 204. Accepted for later processing → 202.
  • Body is malformed or the request is wrong → 400. Body is valid JSON but fails validation rules → 422 (FastAPI uses 422 for this).
  • Not logged in → 401. Logged in but no permission → 403. No such resource → 404.
  • Duplicate or conflicting state (email already exists, version mismatch) → 409.
  • Too many requests → 429 with Retry-After. Unexpected bug → 500. Never return 200 with {"error": ...}.

3.1Virtual environment and pip

A virtual environment gives each project its own packages, so projects do not break each other.

3.2Type hints

Type hints say what type a variable should be. Python itself does not enforce them, but FastAPI and Pydantic read them at runtime to validate input, convert types and generate documentation. This is the secret of FastAPI.

str | None means "may be missing". Older code writes Optional[str]; it is the same thing.

3.3Decorators

A decorator is a function that wraps another function to add behaviour. When you write @app.get("/") in FastAPI, you use a decorator that registers your function as a route.

3.4Generators, yield and context managers

A function with yield gives back values one by one and can pause. FastAPI uses this for dependencies with cleanup (open a database session, yield it, then close it) and for lifespan events.

3.5async / await

Some work is just waiting: for a database, another API, a file. While one task waits, Python can run another. That is what async code does. It uses one thread and an event loop that switches between tasks whenever one says await.

  • async def f() creates a coroutine function. Calling it returns a coroutine object; it does not run yet.
  • await x means "pause me here until x is done, let others run meanwhile". You can only use it inside async def.
  • asyncio.run(main()) starts the event loop (only needed in scripts; FastAPI does it for you).
Never use time.sleep() in async code

time.sleep() blocks the whole event loop; nobody else runs. Use await asyncio.sleep(). We study this in depth in Chapter 13.

3.6Dataclass vs Pydantic (preview)

A dataclass stores data but does not validate it. Pydantic models validate and convert data. That is why FastAPI uses Pydantic.

4.1What is FastAPI?

FastAPI is a modern Python web framework for building APIs. It is built from two libraries:

  • Starlette — the web part: routing, middleware, requests, responses, WebSockets.
  • Pydantic — the data part: validation and conversion using type hints.

FastAPI adds dependency injection, security helpers and automatic OpenAPI documentation on top.

FeatureWhat you get
FastPerformance similar to Node.js and Go frameworks, because it is async and built on Starlette
Fast to codeLess code and fewer bugs; editor auto-complete works everywhere
Automatic validationWrong input gives a clear 422 error, with no code from you
Automatic docsSwagger UI (/docs) and ReDoc (/redoc)
StandardsOpenAPI and JSON Schema, so you can generate client code in any language

4.2WSGI vs ASGI, and what Uvicorn does

A Python web app cannot listen on the network by itself. A server does that and calls your app. The interface between them is a standard:

  • WSGI (old, used by Flask and Django classic): synchronous. One request occupies one worker until finished. No WebSockets.
  • ASGI (new, used by FastAPI): supports async, WebSockets, long-lived connections.

Uvicorn is an ASGI server. It receives the HTTP bytes and calls your app.

4.5def or async def?

You can use both. Short rule (full story in Chapter 13):

  • Inside the function you await something (async DB, httpx) → use async def.
  • You call normal blocking code (regular DB driver, requests, heavy calculation) → use plain def. FastAPI runs it in a thread pool so the server stays responsive.
  • Not sure? Use def. It is safe.

9.1The idea

Dependency Injection (DI): instead of a function creating what it needs (a database session, the current user, settings), it declares what it needs and the framework provides it. In FastAPI you declare with Depends(...).

Why? (1) No repeated code. (2) Easy to replace in tests. (3) Shared logic like auth is in one place. (4) Dependencies can have their own dependencies.

Authentication & Authorization

Passwords, JWT tokens, protected routes and roles. Security topics are asked in almost every interview.

After this chapter you can:

11.1Concepts

  • Authentication (AuthN) = who are you? (login). Authorization (AuthZ) = what are you allowed to do? (permissions).
  • Session: server stores login state, browser holds a session ID cookie. Token: the client holds a signed token and sends it every time; the server stores nothing (stateless, fits REST).
  • Password hashing: never store passwords, only a slow salted hash (Argon2 or bcrypt). Hashing is one-way; you compare hashes on login. Do not use MD5/SHA-1/plain SHA-256.

11.2What is a JWT?

A JSON Web Token has three Base64 parts separated by dots: header.payload.signature.

JWT is signed, not encrypted

Anyone can read the payload (paste one into jwt.io). The signature only proves nobody changed it. So never put secrets in a JWT. Always set a short exp. Keep SECRET_KEY in an environment variable.

11.3Complete example

11.4Beyond the basics

  • Access + refresh tokens: access token lives 5–15 minutes; a longer-lived refresh token (days) gets a new access token. Store refresh tokens safely and allow revoking them.
  • OAuth2 / OpenID Connect: "Login with Google". You redirect the user to the provider, get a code, exchange it for tokens. Use a library (Authlib) or a service (Auth0, Keycloak, Clerk).
  • API keys: simple secret in a header for server-to-server calls. Store only a hash of it.
  • Scopes: fine-grained permissions such as items:read, items:write, stored in the token.
  • Common attacks: brute force (add rate limits and lockouts), token theft (HTTPS, short expiry), IDOR (user 5 reads /orders/9 that belongs to user 6 — always check ownership!), SQL injection, mass assignment.

Async Deep Dive & Concurrency

The topic where good candidates become great ones: what really happens when your endpoint waits.

13.1Concurrency vs parallelism

  • Concurrency: many tasks in progress at once (one cook switching between pots while waiting for water to boil).
  • Parallelism: many tasks running at the same instant (many cooks, many CPU cores).
  • I/O-bound work waits for the network/disk/database → async or threads help a lot. CPU-bound work computes (image processing, ML inference) → needs multiple processes/cores.
  • GIL (Global Interpreter Lock): in normal CPython only one thread runs Python bytecode at a time. So threads do not speed up CPU-bound Python, but they do help I/O-bound code because the lock is released while waiting.

13.2How FastAPI runs your endpoint

You writeFastAPI doesGood for
async defRuns it directly on the event loopawait-able I/O: async DB, httpx, async Redis

The #1 async mistake

Calling blocking code (time.sleep, requests.get, a sync DB query, heavy loops) inside async def. The single event-loop thread is frozen, so every other request waits. The server looks "hung" even though CPU is idle.

Test it: open two terminals and call /bad twice at the same time. Then do the same with /good-async. Compare the total time.

13.3Running things concurrently

  • asyncio.gather(*coros) runs them together and returns results in order. Add return_exceptions=True to get errors as values instead of failing everything.
  • asyncio.create_task(coro) starts a task in the background; async with asyncio.TaskGroup() (3.11+) is the safe, structured version.
  • asyncio.wait_for(coro, timeout=2) or async with asyncio.timeout(2): stops waiting after a time limit.
  • asyncio.Semaphore(5) limits how many run at once (be kind to other servers).

13.4Blocking code inside async: use a thread

13.5CPU-bound work and scaling

  • Several server processes: uvicorn app.main:app --workers 4 (or fastapi run --workers 4). Each worker has its own event loop and memory. Use about one worker per CPU core.
  • Process pool for CPU tasks inside one app: loop.run_in_executor(ProcessPoolExecutor(), fn, arg).
  • Task queue (Celery / ARQ / RQ) for long jobs: the API returns 202 Accepted and a job ID; a separate worker does the work.
  • Remember: with several workers, in-memory data (like our dict "database" or a Python-level cache) is not shared. Use Redis or a database.
Interview: "Is FastAPI faster than Flask because of async?"

Partly. For I/O-bound workloads with many concurrent connections, async gives higher throughput because one process handles thousands of waiting requests. It does not make CPU-heavy code faster, and a badly written async endpoint (blocking call) can be slower than a normal def. Other reasons for speed: Starlette, Pydantic v2 (Rust core), Uvicorn.

16.1Pagination that scales

Offset paging (?skip=100000&limit=20) makes the database count and skip 100,000 rows. Cursor (keyset) paging says "give me items after id 4711": the database uses the index and stays fast.

16.2Caching

  • HTTP caching: the client or a CDN keeps the response. Set Cache-Control: public, max-age=60. With an ETag, the client can ask "did it change?" and get a tiny 304 Not Modified.
  • Application cache (cache-aside): look in Redis first; on a miss, load from the DB and store in Redis with a time-to-live (TTL).
  • The hard part is invalidation: when data changes, delete or update the cached copy. Keep TTLs short if unsure.

16.3Rate limiting

Protect your API from abuse and accidents. Return 429 Too Many Requests with a Retry-After header.

Sliding windowN requests in the last 60 sSmoother, more memory

With many workers/servers the counters must live in a shared store (Redis), or be enforced at the API gateway / reverse proxy.

16.4Versioning in FastAPI

Announce old versions as deprecated (deprecated=True, Sunset header) and give clients time to migrate.

16.5Idempotency for POST

A user double-clicks "Pay". Without protection you charge twice. Let the client send Idempotency-Key: <uuid>. Server logic: if the key was seen, return the stored response; else process and store key → response (with TTL).

  • Tracing: follow one request across many services (OpenTelemetry).

A. HTTP and REST
1. What is REST? Is it a protocol?
REST is an architectural style, not a protocol or standard. Resources are identified by URLs and manipulated with standard HTTP methods; servers are stateless; responses describe their cacheability. An API following these ideas is "RESTful".
2. Name the REST constraints.
Client–server, stateless, cacheable, uniform interface, layered system, and (optional) code on demand.
3. What does "stateless" mean and why is it useful?
Each request carries everything the server needs (e.g. a token). The server keeps no client session between requests. Benefit: any server instance can handle any request, so horizontal scaling and failover are easy. Cost: a bit more data per request.
4. Which HTTP methods are safe? Which are idempotent?
Safe (no state change): GET, HEAD, OPTIONS. Idempotent (same effect if repeated): GET, HEAD, OPTIONS, PUT, DELETE. POST is neither. PATCH is not guaranteed idempotent.
5. PUT vs PATCH vs POST?
POST creates (server chooses the ID) or triggers an action. PUT replaces the whole resource at a known URL (idempotent). PATCH changes only the sent fields.
6. How do you make a POST safe to retry?
Use an Idempotency-Key header. The server stores the key with the first result and returns that stored result for repeats. Essential for payments and order creation.
7. 401 vs 403?
401: not authenticated (missing/invalid credentials). 403: authenticated but not permitted. (Some APIs return 404 instead of 403 to hide that a resource exists.)
8. 400 vs 422?
400: the request is malformed or generally bad (e.g. broken JSON). 422: syntax is fine but the content fails validation rules. FastAPI returns 422 for validation errors.
9. 200 vs 201 vs 202 vs 204?
200 success with a body. 201 created (send Location). 202 accepted, processing later (async jobs). 204 success with no body (typical for DELETE).
10. What is HATEOAS?
"Hypermedia as the engine of application state": responses include links to related actions so clients discover them instead of hard-coding URLs. It is Level 3 of the Richardson model; few APIs implement it fully.
11. How do you version an API?
Most common: URL path (/v1/). Alternatives: header or media type, query parameter. Version only for breaking changes; adding optional fields is not breaking. Deprecate old versions with notice and a sunset date.
12. Offset vs cursor pagination?
Offset (skip/limit): simple, page jumping, but slow on large offsets and unstable when data changes. Cursor (keyset): fast via index and stable, but no random page access.
13. What happens when you type a URL in the browser?
Parse URL → DNS lookup → TCP connect → TLS handshake → HTTP request → server (load balancer → app → DB) → response → browser renders and fetches sub-resources.
14. REST vs GraphQL vs gRPC?
REST: simple, cacheable, universal. GraphQL: client picks fields, one endpoint, avoids over/under-fetching, but harder caching and security. gRPC: binary Protobuf over HTTP/2, very fast, streaming, best for internal microservices, weak browser support.
15. What is CORS and what is a preflight request?
A browser security rule that blocks cross-origin JS from reading responses unless the server allows it via Access-Control-Allow-* headers. For non-simple requests the browser first sends an OPTIONS preflight to ask if the real request is allowed. Only browsers enforce it.
16. How does HTTP caching work?
Cache-Control (max-age, no-store, private/public) sets rules. ETag + If-None-Match or Last-Modified + If-Modified-Since enable conditional requests; unchanged data returns 304 with no body.
17. Cookies vs sessions vs JWT?
Cookie: small data stored by the browser, sent automatically. Session: server-side state referenced by a session-ID cookie. JWT: signed self-contained token the client sends; stateless, but hard to revoke before expiry and must not hold secrets.
18. HTTP/1.1 vs HTTP/2 vs HTTP/3?
1.1: text, requests queue on a connection. 2: binary, multiplexing many streams on one connection, header compression. 3: HTTP over QUIC (UDP), no head-of-line blocking at the transport level, faster on lossy networks.
19. How do you secure a REST API?
HTTPS; strong authentication (OAuth2/JWT), authorization on every resource (avoid IDOR); input validation; hashed passwords; rate limiting; strict CORS; no secrets in code; minimal data in responses; logging and monitoring; updated dependencies.
20. What is rate limiting and how would you implement it?
Cap requests per client per time window and return 429 with Retry-After. Algorithms: fixed window, sliding window, token bucket. Implement at the gateway or with a shared store (Redis) so all instances agree.
B. FastAPI
21. What is FastAPI and why is it fast?
A Python web framework for APIs built on Starlette (web) and Pydantic (validation). Fast because of ASGI + async support, the Uvicorn server, and Pydantic v2's Rust core. It is also fast to develop with: type hints give validation, docs and editor help.
22. FastAPI vs Flask vs Django?
Flask: minimal, sync (WSGI), you assemble everything. Django: full-stack batteries (ORM, admin, auth); Django REST Framework for APIs. FastAPI: API-first, async, automatic validation and docs, modern typing. Choose FastAPI for APIs/microservices/ML serving; Django for content-heavy sites needing admin and ORM.
23. WSGI vs ASGI?
WSGI is the old synchronous interface (one request per worker at a time, no WebSockets). ASGI is the async successor supporting concurrency, WebSockets and streaming. FastAPI runs on ASGI servers like Uvicorn or Hypercorn.
24. What is Pydantic and what changed in v2?
A data validation library using type hints. v2 is rewritten with a Rust core (much faster) and renamed things: model_dump, model_validate, field_validator, model_validator, ConfigDict(from_attributes=True).
25. How does FastAPI validate a request? What is a 422?
It inspects your function's type hints, builds Pydantic validators for path/query/header/body parameters, validates the incoming data, and on failure raises RequestValidationError, returned as HTTP 422 with a detail list (loc, msg, type).
26. How does FastAPI know if a parameter is path, query or body?
Name in the path template → path. Simple scalar type → query. Pydantic model (or Body()) → body. Explicit Header(), Cookie(), Form(), File() override.
27. What is response_model for?
It declares the output schema: FastAPI validates and filters the returned data to it (hiding fields like passwords) and documents it in OpenAPI.
28. Explain dependency injection in FastAPI.
You declare what you need with Depends(callable); FastAPI resolves sub-dependencies, caches results per request, and passes them in. Used for DB sessions, current user, pagination, settings. Dependencies with yield run cleanup after the response. Overridable in tests via app.dependency_overrides.
29. def vs async def endpoints?
async def runs on the event loop: only use with awaitable I/O. def runs in a thread pool: use with blocking libraries. Blocking code inside async def freezes the whole server.
30. What happens if you call time.sleep() or requests.get() inside async def?
It blocks the event loop thread, so all other requests on that worker wait. Fix: use await asyncio.sleep/httpx.AsyncClient, or change to def, or wrap with run_in_threadpool.
31. Middleware vs dependency?
Middleware wraps every request/response (logging, CORS, headers) and works before routing. Dependencies run only for routes that declare them, get validated inputs and can return values (auth, DB session). Use middleware for cross-cutting technical concerns, dependencies for per-route logic.
32. BackgroundTasks vs Celery?
BackgroundTasks runs a function in the same process after the response: simple, but lost if the process dies, no retries, competes for the same resources. Celery/ARQ/RQ use a broker and separate workers: reliable, retries, scheduling, scalable.
33. What are lifespan events?
An async context manager passed as FastAPI(lifespan=...). Code before yield runs at startup (create clients, load model), code after at shutdown. Replaces deprecated on_event.
34. How does FastAPI generate docs?
From your routes, type hints, models and docstrings it builds an OpenAPI schema (/openapi.json) and serves Swagger UI (/docs) and ReDoc (/redoc) from it. The same schema can generate client SDKs.
35. How do you implement JWT auth?
Login endpoint verifies the password hash and returns a signed JWT with sub and exp. A get_current_user dependency uses OAuth2PasswordBearer to read the token, decodes/verifies it, loads the user, or raises 401. Role checks are further dependencies raising 403.
36. How do you test a FastAPI app?
pytest + TestClient (or httpx.AsyncClient with ASGITransport). Override get_db with a test database and auth dependencies with fakes; use fixtures for setup/teardown and parametrize edge cases.
37. How do you structure a large FastAPI project?
Packages by feature/domain (users/, orders/), each with router.py, schemas.py, models.py, service.py (business logic), plus core/ (config, security, db) and tests/. Routers only do HTTP; services hold logic; repositories/DB code stay separate.
38. How do you handle configuration and secrets?
pydantic-settings reads environment variables/.env into a typed Settings class, cached with lru_cache. Secrets come from the platform's secret manager, never from git.
39. How do you customize error responses?
@app.exception_handler(SomeException) returning JSONResponse. Override RequestValidationError for the 422 format and add a generic Exception handler for 500s that logs and hides details.
40. How do you handle file uploads?
UploadFile parameter (needs python-multipart); it spools large files to disk. Validate size and real content type, generate your own filename, store in object storage (S3) for production.
41. How do you deploy FastAPI?
Docker image → Uvicorn workers (about one per core) or many containers → reverse proxy/load balancer for TLS → health checks → CI/CD; migrations as a separate step; logs to stdout; secrets from env.
42. How do you serve an ML model with FastAPI?
Load the model in lifespan once; validate input with Pydantic; sync def endpoint (thread pool) or a queue for heavy jobs; batch endpoint; /ready check; version in responses; stream LLM output with SSE; scale by containers, watch memory per worker; monitor latency and drift.
43. How do you use WebSockets in FastAPI?
@app.websocket("/ws"), await ws.accept(), loop on receive_text()/send_text(), catch WebSocketDisconnect. Keep a connection manager for broadcast. For multiple servers, use Redis pub/sub to share messages.
44. Why do routes like /users/me have to be declared before /users/{id}?
Routes are matched in declaration order. The dynamic route would capture "me" first and fail validation.
45. How do you avoid returning sensitive fields?
Separate input/output schemas and always set response_model (or a return annotation) so only declared fields are returned.
46. How to do partial updates correctly?
PATCH with a model where every field is optional; use data.model_dump(exclude_unset=True) so only fields actually sent are changed, then model_copy(update=...) or set attributes on the ORM object.
C. Python and async
47. Explain the event loop, coroutine and task.
The event loop is a scheduler running in one thread. A coroutine is what async def returns; it runs only when awaited or scheduled. A task wraps a coroutine so the loop runs it concurrently. await is a point where the coroutine yields control.
48. What is the GIL?
A lock in CPython allowing one thread to execute Python bytecode at a time. Threads don't speed up CPU-bound Python but do help I/O-bound work. Use multiple processes for CPU parallelism.
49. gather vs create_task vs TaskGroup?
gather: run many awaitables, collect results in order. create_task: start one in the background (keep a reference!). TaskGroup (3.11+): structured concurrency; if one task fails, the others are cancelled and errors are grouped.
50. What is a decorator? Generator?
Decorator: a function that takes a function and returns a wrapped version (@app.get registers routes). Generator: a function with yield that produces values lazily and can pause; FastAPI uses it for dependencies with cleanup.
51. Do Python type hints enforce types?
No, not by themselves. Tools read them: mypy statically, Pydantic and FastAPI at runtime for validation and docs.
52. Threads vs processes vs async — when to use each?
Async: many I/O waits with async libraries. Threads: blocking I/O libraries. Processes: CPU-bound work or isolation. Mixed systems often use all three.
D. Databases and architecture
53. What is the N+1 problem and how do you fix it?
1 query for a list plus N queries for each item's relation. Fix with eager loading (selectinload/joinedload) or a JOIN/IN query.
54. What are ACID and transactions?
Atomicity (all or nothing), Consistency (rules hold), Isolation (concurrent transactions do not corrupt each other), Durability (committed data survives crashes). A transaction groups statements so they succeed or fail together.
55. Why and when to add an index?
An index (usually a B-tree) makes lookups, sorting and joins on a column fast, at the cost of slower writes and more storage. Index columns used in WHERE, JOIN, ORDER BY; check with EXPLAIN.
56. SQL vs NoSQL?
SQL: relational, strong schema and transactions, joins. NoSQL: flexible schema and horizontal scale (document, key-value, wide-column, graph). Start with PostgreSQL unless you have a specific need.
57. What is connection pooling?
Reusing a fixed set of open DB connections instead of opening one per request (opening is expensive). Watch pool size × workers against the database's connection limit.
58. Explain cache-aside and cache invalidation.
Read: check cache, on miss read DB and store with TTL. Write: update DB and delete/refresh the cache entry. Risks: stale data and cache stampede (many misses at once); mitigate with TTLs, locking, jitter.
59. Why use a service layer / repository pattern?
Routers stay thin (HTTP only), business rules live in services and are unit-testable without HTTP, data access is isolated so you can change the database or mock it.
60. Why use migrations?
They version your schema changes in code so every environment can be upgraded (and rolled back) reproducibly. Alembic is the standard for SQLAlchemy.
E. Scenario and design questions
61. Your endpoint is suddenly slow. How do you investigate?
Reproduce and measure (logs, APM/tracing, p95 latency). Find the layer: DB (slow queries, missing index, N+1), external calls (timeouts), blocking code in async def, CPU, memory/GC, connection pool exhaustion. Fix the biggest bottleneck, then add caching, pagination, or concurrency as needed, and add an alert.
62. Design a URL shortener API.
POST /links {url} → 201 {code, short_url}; GET /{code} → 301/302 redirect; GET /links/{code}/stats. Generate codes with base62 of an auto-increment ID or random ID with a uniqueness check; index on code; cache hot codes in Redis; rate limit creation; validate URLs; handle expiry.
63. Design an upload service for large files.
Don't stream big files through the API. POST /uploads returns a pre-signed URL for object storage (S3); client uploads directly; storage notifies (or client confirms) and a background worker scans/processes it; API stores metadata and status.
64. How would you handle 10,000 requests/second?
Stateless app servers behind a load balancer, many workers/containers, async I/O, connection pools, caching (CDN + Redis), read replicas, pagination, rate limiting, queue for slow work, autoscaling, and load testing to find real limits.
65. Design the API for a payment endpoint.
POST with an Idempotency-Key; validate amounts with Decimal/integers in minor units; authenticate and authorize; DB transaction; return 201 with payment ID; use webhooks for async status updates; audit log; never log card data; rate limit.
66. Serve an LLM feature that takes 30 seconds per answer.
Stream tokens with SSE so users see progress; or use the job pattern (202 + polling/webhook). Limit concurrency and input size, set timeouts, add per-user rate limits and cost controls, cache repeated prompts, keep API keys server-side.

Commands you should know by heart

One-minute explanations

  • REST: resources + URLs + standard methods + stateless + cacheable; usually JSON over HTTP.
  • FastAPI: Starlette (web) + Pydantic (data) + type hints → validation, docs, DI, async.
  • Pydantic: turns type hints into runtime validation and conversion.
  • Depends: declare needs, framework provides them; overridable in tests.
  • async vs def: event loop vs thread pool; never block the loop.
  • JWT: signed (not encrypted) token with claims and expiry; verify signature and exp on every request.
  • Idempotent: repeating gives the same server state; PUT and DELETE yes, POST no.
